  - 쓸 내용: ① 출력 전체(코드 상자에 붙여 넣기) ② 서버 터미널의 `[알림 받음]` 줄 수 ③ 단계 3 의 올린 횟수

  ③ 단계 3 의 올린 횟수 : 4번

- (나) 🔍 `TCK-1` 은 20분 점검에서 1단계로 에스컬레이션되었지만, 60분 점검에서는 에스컬레이션되지 않았습니다. 그 이유를 설명해 주세요. 이때 25분에 변경된 상태와 `needs_escalation` 의 조건을 근거로 쓰고, 이 조건이 없을 때 발생하는 문제도 함께 설명해 주세요.
  - 쓸 내용: ① TCK-1 의 20분 · 25분 · 60분 점검 결과 ② `needs_escalation` 의 조건 ③ 이 조건이 없을 때의 문제
  - 답: ① TCK-1 의 20분 · 25분 · 60분 점검 결과 : 
    20분 점검에서는 TCK-1의 응답 기한인 15분을 5분 초과했고, 티켓 상태가 '열림'이었으므로 1단계로 에스컬레이션되었다.
    25분에는 담당자 kim.sec이 티켓을 확인하기 시작하여 상태를 '열림'에서 '확인 중'으로 변경했다.
    60분 점검에서는 응답 기한을 이미 초과했지만 티켓 상태가 '확인 중'이므로 다시 에스컬레이션되지 않았다.
  ② `needs_escalation` 의 조건 : 티켓 상태가 '열림'이고 현재 시각이 응답 기한 이상일 때만 True를 반환한다. 반대로 '확인 중'이나 '해결' 상태이면 False를 반환하여 에스컬레이션 대상에서 제외한다.
  ③ 이 조건이 없을 때의 문제 : 이미 담당자가 확인하고 있거나 해결한 티켓까지 반복해서 에스컬레이션될 수 있다. 그 결과 불필요한 상급자 알림이 발생하고, 담당자의 업무가 중복되거나 실제로 아직 확인되지 않은 중요한 티켓을 구분하기 어려워질 수 있다.

- (다) 🔍 110분 점검에서 `TCK-3` 은 2단계로, `TCK-6` 은 1단계로 에스컬레이션되었습니다. 두 티켓의 응답 기한과 초과 시간을 근거로 단계가 달라진 이유를 설명해 주세요. 또한 등급 low 인 `TCK-2` 가 에스컬레이션되지 않은 이유도 설명해 주세요.
  - 쓸 내용: ① TCK-3 · TCK-6 의 응답 기한과 넘긴 시간 ② 단계가 달라진 이유 ③ TCK-2 가 에스컬레이션되지 않은 이유
  - 답: ① TCK-3 · TCK-6 의 응답 기한과 넘긴 시간 : TCK-3의 응답 기한은 68분이고 점검 시각은 110분이므로, 110 - 68 = 42분을 초과했다. TCK-6의 응답 기한은 95분이고 점검 시각은 110분이므로, 110 - 95 = 15분을 초과했다.
  ② 단계가 달라진 이유 : 에스컬레이션 단계는 응답 기한을 얼마나 초과했는지에 따라 결정되기 때문이다. TCK-3은 42분을 초과하여 2단계 조건을 만족했고, TCK-6은 15분을 초과하여 1단계 조건을 만족했다. 따라서 같은 mid 등급이더라도 응답 기한과 초과 시간이 다르면 에스컬레이션 단계가 달라질 수 있다.
  ③ TCK-2 가 에스컬레이션되지 않은 이유 : TCK-2는 low 등급으로 응답 기한이 243분이다. 110분 점검 시각을 기준으로 계산하면 110 - 243 = -133분이므로 아직 응답 기한까지 133분이 남아 있다. 따라서 응답 기한을 초과하지 않아 에스컬레이션 대상에서 제외되었다.

- (나) 🔍 확인된 티켓 `TCK-1` · `TCK-3` · `TCK-4` · `TCK-6` · `TCK-7` 의 확인 시간(확인 시각 − 생성 시각)을 각각 계산하고, 그 평균인 MTTA(평균 확인 시간)를 직접 계산해 적어 주세요. 또한 미확인 티켓인 `TCK-2` · `TCK-5` 를 평균에서 제외하는 이유도 설명해 주세요.
  - 쓸 내용: ① 확인한 티켓 5장의 확인 시간 계산 ② 평균 ③ 확인하지 않은 티켓을 뺀 이유
  - 답: ① 확인한 티켓 5장의 확인 시간 계산 : 
  TCK-1: 10분 - 0분 = 10분
  TCK-3: 80분 - 8분 = 72분
  TCK-4: 140분 - 12분 = 128분
  TCK-6: 90분 - 35분 = 55분
  TCK-7: 105분 - 95분 = 10분
  ② 평균 : (10 + 72 + 128 + 55 + 10) ÷ 5 = 275 ÷ 5 = 55.0분 따라서 MTTA는 55.0분이다.
  ③ 확인하지 않은 티켓을 뺀 이유 : TCK-2와 TCK-5는 아직 담당자가 확인하지 않아 첫 확인 시각인 acked_at 값이 -1이기 때문이다. 실제로 확인한 시각이 없으므로 확인까지 걸린 시간을 계산할 수 없으며, 이번 MTTA에서는 확인된 티켓만 평균에 포함한다. 다만 미확인 티켓은 별도로 관리하고 응답 기한을 초과했는지 확인해야 한다.

- (다) 🔍 응답 기한을 위반한 티켓 2장이 어느 티켓인지 적어 주세요. 이때 각 티켓의 `sla_due` 와 확인 시각을 근거로 씁니다. 그리고 단계 1 의 70분 · 80분 · 110분에 출력된 줄(상급자에게 올림 · 확인 중)이 이 두 티켓과 어떤 관계인지 설명해 주세요.

  - 답: ① 기한을 넘긴 티켓과 `sla_due` · 확인한 시각 : 응답 기한을 위반한 티켓은 TCK-3과 TCK-4이다.
  TCK-3의 응답 기한(sla_due)은 68분이고 실제 확인 시각은 80분이므로 12분을 초과했다.
  TCK-4의 응답 기한(sla_due)은 72분이고 실제 확인 시각은 140분이므로 68분을 초과했다.
  따라서 두 티켓 모두 응답 기한보다 늦게 확인되어 SLA 위반으로 집계되었다.
  ② 단계 1 의 70분 · 80분 · 110분 줄과의 관계 : 70분에는 TCK-3이 응답 기한을 2분 넘겼지만 아직 확인되지 않아 1단계 에스컬레이션되었다. 80분에는 담당자 lee.soc이 TCK-3을 처음 확인하여 '확인 중' 상태로 변경했다. 그러나 응답 기한보다 12분 늦었으므로 SLA 위반에 해당한다. 같은 80분에 TCK-4도 응답 기한을 8분 넘긴 상태였으므로 1단계 에스컬레이션되었다. 110분에는 TCK-4가 여전히 확인되지 않았고 응답 기한을 38분 초과했기 때문에 2단계로 에스컬레이션되었다. 이후 TCK-4는 140분에 처음 확인되어 최종적으로 응답 기한을 68분 위반했다.
