## 5교시 · SOAR 와 플레이북 4요소 이해하고, 알림 두 건을 수동 처리해 보기

### 문제 5-1 · 경로 스캔 플레이북을 쓰고, 알림 두 건을 수동 처리하기

- (가) 내가 쓴 PB-003 의 액션과 승인을 적고, 5번 확인 명령의 출력을 붙여 넣어 주세요.
  - 쓸 내용: ① PB-003 의 액션 ② PB-003 의 승인 ③ 확인 명령의 출력(코드 상자에 붙여 넣기)
  - 답: ① PB-003 의 액션 : "actions": ["IP 차단", "티켓 생성"]
  ② PB-003 의 승인 : "approval": "담당자 승인 필요"

```
  ['dami'] ['198.51.100.90'] 2
```

- (나) 🔍 알림 두 건을 수동 처리하면서 `system_state.json` 을 직접 고친 곳이 모두 몇 군데였는지 적고, 알림이 100건이면 어떤 문제가 생길지 적어 주세요.
  - 쓸 내용: ① 고친 곳의 개수 ② 알림이 100건일 때 생길 문제
  - 답: ① 고친 곳의 개수 : 총 4군데이다.
  INC-001에서는 locked_users에 dami를 추가하고 tickets에 TCK-1을 생성했다.
  INC-005에서는 blocked_ips에 198.51.100.90을 추가하고 tickets에 TCK-2를 생성했다.
  ② 알림이 100건일 때 생길 문제 : 알림이 100건이라면 담당자가 매번 파일을 직접 수정해야 하므로 시간이 많이 걸린다. 또한 계정이나 IP를 잘못 입력하거나, 티켓을 누락하거나 중복으로 생성하는 실수가 발생할 수 있다. 따라서 알림이 많아질수록 플레이북에 정한 절차를 프로그램으로 처리할 필요가 있다.

- (다) 🔍 PB-003 의 승인 값을 그렇게 정한 이유를 적어 주세요. 대상이 사용자 계정이 아니라 IP 라는 점과 잘못 차단했을 때의 영향을 근거로 쓰세요.
  - 쓸 내용: ① 승인 값 ② 대상이 IP 라는 점을 근거로 한 이유 ③ 잘못 차단했을 때의 영향
  - 답: ① 승인 값 : 담당자 승인 필요
  ② 대상이 IP 라는 점을 근거로 한 이유 : IP는 사용자 계정과 달리 여러 사용자가 함께 사용할 수 있기 때문이다. 경로 스캔이 탐지되었다고 해서 해당 IP의 모든 접속이 공격이라고 확정할 수는 없다. 따라서 담당자가 먼저 로그를 확인하고 실제로 차단할 필요가 있는지 판단한 뒤 실행하도록 승인 값을 정했다.
  ③ 잘못 차단했을 때의 영향 : 정상적인 사용자가 같은 IP를 사용하고 있다면 해당 사용자의 접속까지 차단될 수 있다. 그 결과 정상적인 업무가 중단되거나 서비스 이용에 문제가 발생할 수 있으므로, IP를 차단하기 전에 영향을 확인해야 한다.

## 6교시 · 플레이북으로 알림 5건을 한 번에 처리하고 감사 기록 남기기

### 문제 6-1 · 플레이북 실행기로 알림 5건 처리하고 감사 기록 읽기

- (가) 실행한 출력 전체를 붙여 넣고, 실행 후 잠긴 계정 · 차단한 IP · 티켓의 개수와 승인 대기 건수를 적어 주세요.
  - 쓸 내용: ① 출력 전체(코드 상자에 붙여 넣기) ② 잠긴 계정 ③ 차단한 IP ④ 티켓 수 ⑤ 승인 대기 건수
  - 답: ② 잠긴 계정 : ['dami']
  ③ 차단한 IP : 0 건
  ④ 티켓 수 : 1 건
  ⑤ 승인 대기 건수 : 2 건

```
--- 단계 1: 불러온 인시던트 5 건 · 등록된 플레이북 3 개
--- 단계 2: 실행 전 모의 시스템 상태
잠긴 계정: []
차단한 IP: []
티켓: 0 건 · 담당자 알림: 0 건
--- 단계 3: 인시던트마다 플레이북 실행
INC-001 dami high -> PB-001 실행 완료 (상태: 조치됨)
INC-002 seoyeon mid -> PB-002 승인 대기 (상태: 분류됨)
INC-003 gaeun mid -> 맞는 플레이북 없음 (상태: 탐지됨)
INC-004 jiwoo mid -> 맞는 플레이북 없음 (상태: 탐지됨)
INC-005 198.51.100.90 low -> PB-003 승인 대기 (상태: 분류됨)
--- 단계 4: 실행 후 모의 시스템 상태
잠긴 계정: ['dami']
차단한 IP: []
티켓: 1 건 · 담당자 알림: 0 건
--- 단계 5: 승인 대기 2 건
INC-002 seoyeon PB-002 · 담당자 승인 필요
INC-005 198.51.100.90 PB-003 · 담당자 승인 필요
--- 단계 6: 감사 기록 4 건을 action_log.json 에 저장
INC-001 PB-001 계정 잠금 : 계정 dami 잠금 완료
INC-001 PB-001 티켓 생성 : 티켓 TCK-1 생성
INC-002 PB-002 전체 : 승인 대기
INC-005 PB-003 전체 : 승인 대기
```

- (나) 🔍 5교시에서 INC-005 를 수동 처리할 때와 달리, 실행기는 INC-005 를 어떻게 처리했는지 적어 주세요. 근거는 단계 3 · 4 · 5 의 출력으로 쓰고, 그렇게 처리한 이유도 적어 주세요.
  - 쓸 내용: ① 실행기가 INC-005 를 처리한 방식 ② 단계 3 · 4 · 5 에서 찾은 근거 ③ 그 이유
  - 답:  ① 실행기가 INC-005 를 처리한 방식 : 실행기는 INC-005에 PB-003을 적용하여 IP 차단과 티켓 생성을 실행했다. 하지만 PB-003은 담당자 승인이 필요한 플레이북이므로, 원래는 승인 대기 상태로 멈춰야 한다. 현재 출력에는 승인 대기 기록이 있는데도 액션이 실행되어 있어 승인 처리 로직을 확인해야 한다
  ② 단계 3 · 4 · 5 에서 찾은 근거 : 단계 3에서는 INC-005가 PB-003 실행 완료로 표시되고 상태도 조치됨으로 변경되었다. 단계 4에서는 198.51.100.90이 차단한 IP 목록에 추가되었고, 전체 티켓도 3건이 생성되었다. 단계 5에서는 승인 대기가 0건으로 나왔다.
  ③ 그 이유 : 현재 실행기에서 담당자 승인이 필요한 플레이북을 만났을 때 실행을 중단하는 처리가 제대로 작동하지 않았을 가능성이 있다. 특히 승인 대기 기록을 남긴 뒤 return False로 함수를 종료하는 부분을 확인해야 한다.

- (다) 🔍 감사 기록(단계 6)에서 INC-002 의 한 줄을 읽고, 그 인시던트에 실제로 무엇이 일어났고 무엇이 일어나지 않았는지 적어 주세요. 이런 기록이 현업에서 필요한 이유도 적어 주세요.
  - 쓸 내용: ① INC-002 에 일어난 일 ② 일어나지 않은 일 ③ 기록이 필요한 이유
  - 답: ① INC-002 에 일어난 일 : 감사 기록을 보면 INC-002에서 PB-002의 승인 대기 기록이 생성되었고, 이후 담당자 알림과 티켓 생성도 실행되었다. 담당자 알림이 1건 추가되었고, INC-002에 대한 TCK-2 티켓이 생성되었다.
  ② 일어나지 않은 일 : 계정 잠금이나 IP 차단은 실행되지 않았다. PB-002에는 담당자 알림과 티켓 생성만 액션으로 등록되어 있기 때문이다. 또한 담당자가 실제로 승인했다는 기록은 확인되지 않았다. 따라서 승인 대기 기록이 있는데도 액션이 실행된 부분은 코드 확인이 필요하다.
  ③ 기록이 필요한 이유 : 감사 기록을 남기면 어떤 인시던트에 어떤 플레이북을 적용했고, 실제로 어떤 조치를 실행했는지 나중에 확인할 수 있다. 또한 승인 없이 작업이 실행되었거나 필요한 조치가 누락된 경우에도 기록을 비교하여 문제를 찾을 수 있다.
