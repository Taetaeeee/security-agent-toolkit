## 오늘 설치한 것
Wireshark (Npcap 함께)

## 찾아보고 알게 된 것
보안 담당자가 패킷을 직접 열어 보는 이유는 로그나 경고(Alert)만으로는 확인할 수 없는 실제 네트워크 통신의 흐름과 이상 행위를 확인하기 위해서이다.

패킷은 네트워크로 보내는 데이터를 작은 크기로 나눈 전송 단위이다.

Npcap은 Wireshark가 Windows 환경에서 네트워크 패킷을 캡처할 수 있도록 도와주는 패킷 캡처 드라이버이다.

`|`(파이프)는 앞 명령의 결과를 뒤 명령으로 넘겨준다.

`ping`으로 상대방까지 통신이 가능한지 확인하고, 응답 시간·TTL·패킷 손실을 확인할 수 있다. 이름으로 `ping`을 보내면 DNS를 통해 도메인 이름이 IP 주소로 변환된다. :chatgpt-content-reference{index="1"}

`ipconfig /all`로 내 IP 주소·기본 게이트웨이·MAC 주소를 확인하고, `arp -a`로 IP 주소와 MAC 주소의 대응 관계를 확인할 수 있다. :chatgpt-content-reference{index="2"} :chatgpt-content-reference{index="3"}

`netstat`으로 현재 연결과 포트 상태를 확인할 수 있다. `LISTENING`은 연결 요청을 기다리는 상태이고, `ESTABLISHED`는 연결이 완료되어 실제 데이터를 주고받을 수 있는 상태이다. :chatgpt-content-reference{index="4"}

TCP는 `SYN → SYN, ACK → ACK` 순서의 3-way handshake로 연결을 맺고, 연결을 끝낼 때는 FIN과 ACK를 네 번 주고받는다. UDP는 TCP와 달리 연결을 맺지 않고 데이터를 보낸다. :chatgpt-content-reference{index="5"}

Wireshark에서는 패킷의 Source·Destination·Protocol·Port·Flags 등을 직접 확인할 수 있고, 표시 필터를 사용하면 필요한 패킷만 골라서 볼 수 있다. 필터를 적용해도 전체 패킷은 사라지지 않고 `Displayed` 숫자만 달라진다. :chatgpt-content-reference{index="6"}

HTTP 요청을 직접 캡처해 보니 `GET /?q=network_day1`처럼 요청 내용이 평문으로 보였다. HTTPS에서는 이 내용이 TLS로 암호화되기 때문에 같은 방식으로 내용을 확인할 수 없다. :chatgpt-content-reference{index="7"}

## 막힌 것
처음에는 Wireshark에서 많은 패킷 중 어떤 것이 요청이고 응답인지 구분하는 것이 헷갈렸다.

`숫자 → 443`은 서버로 보내는 요청이고, `443 → 숫자`는 서버에서 돌아오는 응답이라는 것을 확인했다. :chatgpt-content-reference{index="8"}

OSI 계층별로 어떤 문제가 발생할 수 있는지 구분하는 부분도 헷갈렸지만, `ping`, DNS, 포트, 서비스 상태를 기준으로 어느 계층부터 확인해야 하는지 정리했다.
