# 1과목 회고 (김봉경)

## 내가 만든 것
- 파이썬의 변수, 리스트, 딕셔너리부터 시작해 조건문과 반복문을 이용하여 보안 로그에서 필요한 데이터를 찾고 로그인 실패 횟수 등을 집계하는 코드를 작성했다.
- 함수와 파일 입출력을 사용해 반복되는 작업을 기능별로 분리하고, 로그 데이터를 코드 내부가 아닌 외부 파일에서 읽어 처리하도록 만들었다.
- 예외처리와 logging을 적용해 형식이 잘못된 로그가 포함되어 있어도 전체 프로그램이 중단되지 않는 `log_parser.py`를 만들었다.
- 서로 다른 형태의 로그 데이터를 공통된 구조로 변환하고 JSON으로 저장하는 `normalize_logs.py`를 구현했다.
- 정규표현식을 이용해 일정한 형식이 없는 서버 로그에서 시간, 계정, IP, 이벤트 등의 정보를 추출하고, 브루트포스·의심 IP·심야 로그인과 같은 보안 탐지 규칙을 적용했다.
- `requests`를 이용해 외부 API와 통신하는 `api_client.py`를 만들고, timeout·상태 코드·재시도·환경변수 등을 적용하여 외부 요청이 실패하는 상황까지 처리했다.
- Flask를 이용한 `webhook_server.py`를 만들어 외부에서 발생한 경보를 실시간으로 받을 수 있도록 했고, `curl`과 셸 스크립트를 이용해 요청을 직접 전송하고 확인했다.
- 트리거·조건·액션 구조를 이용해 탐지된 경보를 자동으로 Webhook에 전달하고, 같은 경보가 중복 전송되지 않도록 처리한 뒤 `scheduler_job.py`를 통해 일정한 주기로 자동 실행되도록 구성했다.
- Gemini API를 연결한 `llm_client.py`를 만들어 보안 로그를 LLM에 전달하고, 자연어 분석 결과를 JSON 형태로 받아 프로그램에서 다시 사용할 수 있도록 구현했다.
- AI 에이전트 실습에서는 LLM이 상황에 맞는 도구를 선택하도록 하고, `tool_router.py`에서 선택된 함수를 실제로 실행하도록 연결했으며 위험한 작업에는 사람의 승인을 거치도록 구성했다.
- 여러 개의 보안 경보를 묶음으로 LLM에 전달하여 요약하고 위험도를 `high`, `medium`, `low`로 분류한 뒤 위험도순으로 정렬하는 `event_summarizer.py`를 만들었다.
- 경보 전체를 다시 분석하여 총평을 만들고, 처리 건수·위험 경보·건별 내역을 조합해 사람이 읽을 수 있는 일일 보안 관제 보고서를 생성하는 `report_generator.py`를 구현했다.
- 모델, 승인 기준, 보고서 저장 위치, Webhook 주소와 같이 변경될 수 있는 값을 `config.json`으로 분리하고, `notifier.py`를 통해 알림 서버가 실패하더라도 전체 작업은 계속되도록 예외처리를 적용했다.
- 마지막으로 지금까지 만든 기능들을 `pipeline.py` 하나로 연결하여 설정 읽기 → 경보 분석 → 위험도 정렬 → 보고서 생성 → 사람 확인 대상 판정 → 알림 전송까지의 과정을 `python pipeline.py` 명령 한 번으로 실행할 수 있도록 구성했다.
- `test_agent_core.py`와 assert를 이용해 위험도 정렬, 경고 조건, 출력 형식 등 주요 기능이 수정 이후에도 정상적으로 동작하는지 확인하고, 문법 오류·실행 오류·논리 오류를 직접 찾아 수정하는 과정까지 진행했다.

## 가장 어려웠던 것
- assert lines.splitlines()[0].startswith("- [high]"), "위험도 순이어야 한다."
- splitlines()와 startswith()를 오랜만에 사용하다 보니 문자열을 나누고 첫 번째 줄의 시작 값을 검사하는 과정이 가장 오래 걸렸다.
- 단순히 코드가 실행되는 것뿐만 아니라 결과가 정해 둔 규칙대로 나오는지 확인하는 테스트 과정이 어렵게 느껴졌다.

## 리뷰에서 찾은 것과 고친 것
- 모델 이름처럼 변경될 수 있는 값을 코드에 직접 작성하지 않고 config.json으로 분리해 설정만 변경해도 동작을 바꿀 수 있도록 수정했다.
- 외부 알림 서버가 응답하지 않을 경우 전체 파이프라인까지 중단될 수 있어 timeout과 try/except를 적용하고, 알림 전송에 실패하더라도 보고서는 정상적으로 생성되도록 수정했다.
- high 경보 기준, 위험도 정렬 순서, 출력 줄 수 등을 assert로 검사하여 코드가 실행되더라도 결과가 잘못되는 논리 오류까지 확인하도록 했다.

## 캡스톤에서 더 해 보고 싶은 것
- 지금까지 만든 기능들을 실제 보안 운영 환경과 비슷한 구조로 확장해 보고 싶다.
- 서버나 네트워크 장비에서 발생하는 실제 로그를 자동으로 수집하고, 탐지 규칙과 LLM 분석을 함께 사용해 위험도를 판단하는 기능을 구현해 보고 싶다.
- 중요한 경보가 발생하면 실제 메신저나 알림 채널로 즉시 전달하고, 담당자의 승인 여부에 따라 후속 작업을 수행하도록 만들어 보고 싶다.
- 최종적으로 로그 수집 → 탐지 → 분석 → 보고서 생성 → 알림 → 사람의 승인까지 하나의 흐름으로 이어지는 보안 운영 자동화 시스템을 만들어 보고 싶다.
