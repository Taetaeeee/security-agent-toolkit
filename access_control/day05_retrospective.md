## 상황 2 · 퇴사자 계정으로 요청이 계속 들어옴 (본보기)

- 고칠 파일: `config/users.json`
- 어떻게 고치나요: dami 의 `"employed"` 가 `true` 로 남아 있다면 먼저 `false` 로 바꿉니다. 이미 `false` 이면 그대로 두고, dami 의 항목 전체를 `users.json` 에서 지웁니다.
- 고친 뒤 확인: 같은 요청이 「등록되지 않은 사용자」로 거부되고, 퇴사자 계정 점검이 통과로 바뀌는지 봅니다.
- 더 써 보고 싶은 것(선택): `check_permission` 이 퇴사 여부를 역할 확인보다 먼저 보는 이유는 무엇일까요?

## 상황 3 · 다른 팀 업무를 잠시 지원함
- 원인: 데이터 문제. seoyeon은 월말 정산 대조 업무를 지원하기 위해 SETTLE 권한이 필요하지만, 기존에 등록된 예외 1번의 만료 시간이 지나 권한 없음으로 거부되고 있다.
- 고칠 파일: `config/exceptions.json`
- 어떻게 고치나요: seoyeon에게 해당 권한이 계속 필요한지 확인하고, 보안 담당자의 승인을 받은 뒤 새로운 만료 시각을 정해 예외 권한을 재부여한다.
- 고친 뒤 확인: 설정한 만료 시각 전에는 True, 예외 번호로 허용되는지 확인한다. 만료 시각이 지나면 다시 권한 없음으로 거부되는지도 확인한다.
- 더 써 보고 싶은 것(선택): 예외 권한은 언제까지 유지해야 하고, 연장이 필요할 때 누가 승인해야 할까?

## 상황 4 · 새 권한이 필요함
- 원인: 규칙 문제. junho가 영업 실적 정정을 위해 SALES 권한을 요청했지만, 누가 승인하고 언제까지 처리할지에 대한 절차가 정해져 있지 않다.
- 고칠 파일: `req_create.py`, `req_review.py`, `req_grant.py`, `req_sla.py`
- 어떻게 고치나요: 먼저 req_create.py로 권한 요청서를 생성하고, 요청 이유와 사용 기한을 기록한다. 이후 req_review.py에서 담당자가 요청을 검토하고 승인하면 req_grant.py에서 기간이 정해진 예외 권한을 부여한다. req_sla.py로 처리 기한을 넘긴 요청도 확인한다.
- 고친 뒤 확인: 요청서 상태가 reviewing → approved → granted 순서로 변경되는지 확인한다. 실제로 SALES 권한이 허용되고, 만료된 이후에는 다시 거부되는지 확인한다.
- 더 써 보고 싶은 것(선택): 승인된 요청이라도 사용자가 퇴사했거나 이미 같은 권한이 있다면 어떻게 처리해야 할까?

## 상황 5 · 안 쓰는 권한이 쌓임
- 원인: 사람의 일. 정기 점검에서 seoyeon의 SALES 권한은 120일 동안 사용되지 않았고, gaeun의 ACCOUNT 권한은 사용 이력이 없는 것으로 확인되었다.
- 고칠 파일: `review_unused.py`, `config/exclude_list.json`, `revoke_plan.py`, `revoke.py`
- 어떻게 고치나요: review_unused.py로 90일 넘게 사용하지 않은 권한과 사용 이력이 없는 권한을 회수 후보로 분류한다. 이후 config/exclude_list.json을 확인하여 정기 결산이나 비상 업무에 필요한 권한은 회수 대상에서 제외한다. 회수가 필요한 권한은 계획과 승인 절차를 거쳐 revoke.py에서 처리한다.
- 고친 뒤 확인: 회수 대상과 제외 대상이 올바르게 분류되었는지 확인한다. 실제 회수한 권한은 회수 전후의 접근 판정을 비교하고 회수 이력도 확인한다.
- 더 써 보고 싶은 것(선택): 사용 이력이 없다는 이유만으로 권한을 바로 삭제하면 어떤 문제가 생길까?

## 상황 6 · 민감한 권한을 회수해야 함
- 원인: 규칙 문제. 회수 대상에 쓰기 권한과 여러 사용자에게 영향을 줄 수 있는 권한이 있으므로, 승인 없이 회수하면 정상 업무에 문제가 발생할 수 있다.
- 고칠 파일: `revoke_plan.py`, `revoke_approve.py`, `revoke.py`
- 어떻게 고치나요: 먼저 revoke_plan.py에서 회수 방법과 영향 범위를 확인한다. 이후 revoke_approve.py에서 민감한 권한이거나 영향이 2건 이상이면 승인이 필요한 대상으로 분류한다. 승인된 계획과 승인 불필요 계획만 revoke.py에서 실행하고, 승인 대기 중인 계획은 보류한다.
- 고친 뒤 확인: 민감 권한과 영향이 2건 이상인 계획이 승인 대상으로 분류되는지 확인한다. 승인된 계획만 실행되었는지, 승인 대기 계획은 실행되지 않았는지 확인하고 회수 전후 판정과 이력을 점검한다.
- 더 써 보고 싶은 것(선택): 권한을 회수하기 전에 다른 사용자에게 미치는 영향을 확인해야 하는 이유는 무엇일까?

## 상황 7 · 새벽 외부 접속, 그리고 정상 직원이 계속 거부됨
- 원인: 규칙 문제. 새벽 외부 접속까지 허용되는 것은 접근 조건이 너무 느슨한 문제이고, gaeun이 정상적인 업무를 위해 VPN을 사용하는데 계속 거부된다면 접속 위치 조건이 실제 업무 환경과 맞지 않는 문제일 수 있다.
- 고칠 파일: `config/conditions.json`, `conditional.py`
- 어떻게 고치나요: conditional.py에서 기본 권한을 확인한 다음 업무 시간과 접속 위치를 모두 검사하도록 한다. 새벽 외부 접속은 거부하도록 유지한다. gaeun의 VPN 요청은 먼저 정상 업무인지 확인하고, 정당한 업무상 필요성이 인정되면 보안 담당자 승인 후 conditions.json의 ACCOUNT 허용 위치에 VPN을 추가하는 방안을 검토한다.
- 고친 뒤 확인: 새벽 2시 external 접속은 거부되는지 확인한다. gaeun의 VPN 접속은 승인된 정책에 따라 업무 시간 안에서만 허용되는지 확인한다. 허용되지 않은 시간이나 위치에서는 계속 거부되는지도 확인한다.
- 더 써 보고 싶은 것(선택): 정상 사용자의 편의 때문에 접근 조건을 완화하면 어떤 보안 위험이 발생할까?
