## 5교시 · 접속 로그 한 줄을 조각으로 읽기

### 문제 5-1 · 접속 로그 한 줄에서 주소 · 방법 · 경로 · 상태 코드 꺼내기

- (가) 실행한 출력 전체를 붙여 넣고, 읽기 성공한 줄과 읽기 실패한 줄이 각각 몇 줄인지, 읽기 실패한 줄이 어떤 줄인지 적어 주세요.
  - 쓸 내용: ① 출력 전체(코드 상자에 붙여 넣기) ② 읽기 성공 · 읽기 실패 줄 수 ③ 읽기 실패한 줄이 어떤 줄인지
  - 답: ② 읽기 성공 · 읽기 실패 줄 수 : 읽기 성공 28 줄 · 읽기 실패 2 줄
  ③ 읽기 실패한 줄이 어떤 줄인지 : 
    26줄 198.51.100.21 - - [02/Nov/2026:09:31:40 +0900] "GET /board/5 HTTP/1.1
    30줄 -

```
--- 단계 1: 로그 파일 읽기 - 전체 30 줄
읽기 성공 28 줄 · 읽기 실패 2 줄
--- 단계 2: 로그 첫 3줄을 읽은 결과
{'ip': '198.51.100.21', 'method': 'GET', 'path': '/', 'status': 200}
{'ip': '198.51.100.21', 'method': 'GET', 'path': '/static/app.css', 'status': 200}
{'ip': '198.51.100.34', 'method': 'GET', 'path': '/login', 'status': 200}
--- 단계 3: 값이 덧붙은 요청 (경로에 ? 포함)
192.0.2.15 /board?page=2
192.0.2.15 /search?q=network
```

- (나) 🔍 로그 한 줄만 보고 알 수 있는 것과 알 수 없는 것을 구분해 적어 주세요. 예를 들어 203.0.113.50 의 요청에서 접속자가 누구인지, 로그인에 성공했는지는 알 수 있나요?
  - 쓸 내용: ① 로그 한 줄만 보고 알 수 있는 것 ② 알 수 없는 것 ③ 203.0.113.50 의 요청으로 본 예
  - 답: ① 로그 한 줄만 보고 알 수 있는 것 : 접속을 요청한 IP 주소, 요청 시각, 요청 방법(GET, POST), 요청 경로, HTTP 상태 코드, 응답 크기, 요청 프로그램을 확인할 수 있다.
  ② 알 수 없는 것 : 접속한 사람의 실제 신원이나 정확한 물리적 위치는 확인하기 어렵다. 또한 HTTP 상태 코드만으로 실제 로그인에 성공했는지, 정상 사용자인지 공격자인지도 확정할 수 없다.
  ③ 203.0.113.50 의 요청으로 본 예 : 203.0.113.50에서 처음 GET 요청이 정상 처리된 후, POST 요청에서 401 응답이 5번 발생했다. 이후 POST 요청에 301 응답이 발생하고, 뒤이어 GET 요청에서 403 응답이 2번 발생했다. 이 기록으로 로그인 실패가 반복된 뒤 다른 주소로 이동하는 응답과 접근 거부가 발생했다는 사실은 알 수 있다. 하지만 301 응답만으로 로그인에 성공했다고 확정할 수 없으므로, 실제 인증 로그나 로그인 성공 기록을 추가로 확인해야 한다.

- (다) 🔍 404 가 한 번 난 요청과, 같은 주소에서 `/.env` · `/wp-login.php` · `/phpmyadmin` 이 연달아 404 가 난 요청은 같은 일일까요? 샘플 로그에서 두 경우를 찾아 어떻게 다른지, 왜 한 줄만 봐서는 판단하기 어려운지 적어 주세요.
  - 쓸 내용: ① 한 번의 404 와 연달아 난 404 의 차이 ② 한 줄만 봐서는 판단하기 어려운 이유
  - 답: ① 한 번의 404 와 연달아 난 404 의 차이 : 404가 한 번 발생한 경우에는 사용자가 주소를 잘못 입력하거나 존재하지 않는 페이지를 요청했을 가능성이 있다. 반면 같은 IP 주소에서 /.env, /wp-login.php, /phpmyadmin과 같은 경로를 연속으로 요청했다면 서버의 설정 파일이나 관리 기능을 찾으려는 시도일 수 있다. 따라서 한 번의 404보다 여러 민감한 경로를 연속으로 요청한 경우를 더 주의해서 확인해야 한다.
  ② 한 줄만 봐서는 판단하기 어려운 이유 : 로그 한 줄에는 요청 하나의 정보만 들어 있기 때문에 같은 IP에서 이전에 어떤 요청을 보냈고, 이후에 어떤 경로를 요청했는지 알 수 없다. 따라서 여러 로그를 시간순으로 비교하여 같은 주소에서 요청이 반복되었는지, 특정 경로를 연속으로 탐색했는지 확인해야 한다. 또한 이러한 기록만으로 공격이라고 확정할 수는 없으므로 정상적인 테스트나 관리 작업이었는지도 함께 확인해야 한다.

## 6교시 · 이상 징후 가르기와 SIEM(심)

### 문제 6-1 · 읽은 로그 줄을 정상 · 오류 · 의심으로 가르기

- (가) 실행한 출력 전체를 붙여 넣고, 분류별 요청 수와, 의심으로 분류한 요청 중 같은 주소에서 반복된 것을 적어 주세요.
  - 쓸 내용: ① 출력 전체(코드 상자에 붙여 넣기) ② 분류별 요청 수 ③ 같은 주소에서 반복된 의심 요청
  - 답: ② 분류별 요청 수 : 정상 15 · 오류 5 · 의심 8
  ③ 같은 주소에서 반복된 의심 요청 : 203.0.113.50에서 총 7건의 의심 요청이 발생했다.
  POST /login 요청에서 401이 5번 발생했고, 이후 GET /admin과 GET /admin/users 요청에서 403이 각각 1번 발생했다.
  198.51.100.77에서도 GET /admin 요청이 403으로 거부되었지만, 해당 주소의 의심 요청은 1건이므로 반복된 요청에는 포함되지 않는다.

```
--- 단계 1: 분류별 요청 수 - 전체 28 개
정상 15 · 오류 5 · 의심 8
--- 단계 2: 의심으로 분류한 요청
203.0.113.50 POST /login 401
203.0.113.50 POST /login 401
203.0.113.50 POST /login 401
203.0.113.50 POST /login 401
203.0.113.50 POST /login 401
203.0.113.50 GET /admin 403
203.0.113.50 GET /admin/users 403
198.51.100.77 GET /admin 403
--- 단계 3: 오류로 분류한 요청
198.51.100.90 GET /.env 404
198.51.100.90 GET /wp-login.php 404
198.51.100.90 GET /phpmyadmin 404
198.51.100.21 GET /board/99 404
198.51.100.34 GET /report 500
```

- (나) 🔍 상태 코드와 경로만으로 분류를 정하면 놓치는 것이 있습니다. 샘플 로그에서 놓친 예를 두 가지 찾아(정상이나 오류로 분류됐지만 살펴볼 만한 요청) 왜 놓쳤는지 적어 주세요.
  - 쓸 내용: ① 놓친 예 두 가지 ② 각각 왜 놓쳤는지
  - 답: ① 놓친 예 두 가지 : 
  첫째, 198.51.100.90에서 발생한 /.env, /wp-login.php, /phpmyadmin 요청이다.
  둘째, 203.0.113.50에서 로그인 실패 5번 이후 발생한 POST /login 요청의 302 응답이다.
  ② 각각 왜 놓쳤는지 : 
  첫 번째 요청들은 모두 404로 응답했기 때문에 현재 분류 규칙에서는 오류로 처리된다.
  하지만 같은 IP에서 짧은 시간 동안 설정 파일이나 관리자 페이지와 관련된 경로를 연속으로 요청했다는 점에서 서버 내부의 파일이나 관리 기능을 탐색하려는 시도일 수 있다.
  두 번째 요청은 302 응답이므로 현재 규칙에서는 정상으로 분류된다.
  하지만 같은 IP에서 로그인 요청이 5번 연속 401로 거부된 직후 발생했다는 점에서 추가 확인이 필요하다. 302만으로 로그인 성공을 확정할 수는 없지만, 실제 로그인 여부를 확인할 필요가 있다.
  이처럼 현재 코드는 상태 코드와 경로만 확인하고 요청을 한 줄씩 분류하기 때문에 같은 IP에서 발생한 요청의 순서나 반복된 행동을 파악하지 못한다.

- (다) 🔍 5교시 「현업에서 SIEM(심)을 쓰는 방식 여섯 가지」 표의 방식 중에서, 보안 전담 직원이 1명뿐이고 쓰는 서비스 대부분이 클라우드에 있는 작은 회사라면 어느 방식을 고를지 이유와 함께 적어 주세요. 고르지 않은 방식 하나가 왜 맞지 않는지도 적어 주세요.
  - 쓸 내용: ① 고른 방식과 이유(로그 양 · 인력 · 데이터 위치) ② 고르지 않은 방식 하나와 맞지 않는 이유
  - 답: ① 고른 방식과 이유(로그 양 · 인력 · 데이터 위치) : 관리형 SIEM(Managed SIEM)을 선택하겠다. 해당 회사는 보안 전담 직원이 1명뿐이므로 서버 로그를 수집하고 분석하며 보안 경고에 대응하는 모든 업무를 혼자 처리하기에는 부담이 크기 때문이다. 관리형 SIEM을 사용하면 외부 보안 업체의 도움을 받아 로그 수집과 분석, 보안 이벤트 확인 등의 업무를 수행할 수 있다. 또한 회사에서 사용하는 서비스 대부분이 클라우드에 있으므로 클라우드 서비스의 로그를 연동하기 쉬운 제품을 선택하는 것이 적절하다. 로그 양이 늘어날 때도 수집량에 맞춰 서비스를 조정할 수 있지만, 로그 수집량에 따라 비용이 증가할 수 있으므로 예상 로그 양과 요금 체계를 먼저 확인해야 한다.
  ② 고르지 않은 방식 하나와 맞지 않는 이유 : ① 온프레미스 직접 운영 방식은 선택하지 않겠다.
  회사 안에 별도의 서버와 저장 공간을 구축해야 하고, 시스템 설치부터 업데이트, 로그 관리와 장애 대응까지 직접 수행해야 하기 때문이다. 보안 전담 직원이 1명뿐인 작은 회사에서는 운영 부담이 크고, 대부분의 서비스가 클라우드에 있는 환경에도 상대적으로 비효율적일 수 있다고 생각한다.
