  ③ `finding_count` : 8건

- (나) 🔍 점수와 등급은 코드가 정하고 AI 에게는 요약만 시킨 이유를 적어 주세요. 단계 5 의 확인할 순서와 단계 3 의 요약을 근거로 쓰세요.

  ② 대체 문장이 들어간 대상을 처리하는 방법 : "(요약 실패 — 점수와 이유를 직접 확인)"이라는 문장이 나온 대상은 담당자가 점수와 등급, 탐지된 규칙을 직접 확인해야 한다. AI 요약이 없더라도 점수와 등급은 그대로 유지되므로 확인할 순서에서 제외하지 않고, 원본 로그와 탐지 이유를 살펴보며 조사해야 한다.

## 4교시 · 4과목 총정리: 상황마다 원인과 고치는 방법 정리하기

### 문제 4-1 · 상황 8개의 원인과 고치는 방법을 내 말로 정리하기

**상황 정리** — 상황 1 · 2 · 3 · 4 · 7 · 8 중 4개 이상 씁니다. 상황 5 · 6 은 본보기입니다.

#### 상황 1 · 설정 파일 주소를 연달아 요청했는데 「의심」이 아니라 「오류」로 분류됨
- 원인: 규칙 문제이다. 현재 의심 판정은 401, 403 상태 코드나 /admin 경로를 확인한다. 하지만 해당 IP의 세 요청은 모두 404였고, 의심 판정에 사용하는 경로에도 해당하지 않아 오류로 분류되었다.
- 고칠 파일: log_classify.py의 is_suspicious
- 어떻게 고치나요: /.env, /wp-login.php, /phpmyadmin처럼 의심할 만한 경로를 확인하는 조건을 추가한다.
- 고친 뒤 확인: 해당 IP의 요청 세 개가 의심으로 분류되는지 확인한다.
- 담당자가 가장 먼저 할 일(선택): 요청한 경로와 상태 코드를 확인하고, 같은 IP에서 추가 요청이 있었는지 살펴본다.

#### 상황 2 · 로그 30줄이 이벤트 28개가 됨
- 원인: 데이터 문제이다. 웹 로그 30줄 중 2줄은 형식이 깨져 있어 normalize_web에서 정상적으로 처리되지 않았다.
- 고칠 파일: 웹 로그 정규화 함수 normalize_web이 있는 파일
- 어떻게 고치나요: 제외된 두 줄의 형식을 확인하고, 정상적으로 처리할 수 있는 형식이면 파서를 보완한다. 처리할 수 없는 줄은 별도로 기록하여 누락 여부를 확인할 수 있게 한다.
- 고친 뒤 확인: 원본 30줄 중 정상적으로 처리한 줄과 제외한 줄의 개수를 확인한다.
- 담당자가 가장 먼저 할 일(선택): 제외된 두 줄의 원본 내용을 확인하여 로그가 깨진 이유를 조사한다.

#### 상황 3 · 웹 서버 로그에서 사용자를 알 수 있는 요청이 1개뿐
- 원인: 데이터 문제이다. 웹 로그에는 사용자 이름이 없어서 SaaS 로그인 기록의 IP를 이용해 사용자를 연결하고 있다. 하지만 203.0.113.50은 성공한 SaaS 로그인에서 만든 IP-사용자 대응표에 없으므로 사용자를 알 수 없다.
- 고칠 파일: correlation.py의 make_ip_user_map, attach_user_to_web
- 어떻게 고치나요: 실제 로그인·인증 기록에서 사용자 정보를 추가로 확인할 수 있도록 연결 방식을 보완한다. 사용자가 확인되지 않는 요청은 임의로 연결하지 않는다.
- 고친 뒤 확인: 사용자 정보가 확인된 웹 요청이 정확히 연결되는지 확인하고, 알 수 없는 요청은 그대로 구분되는지 확인한다.
- 담당자가 가장 먼저 할 일(선택): 해당 IP의 로그인 기록과 인증 기록을 확인한다.

#### 상황 4 · 두 로그에 나오는 seoyeon 이 연결되지 않음
- 원인: 규칙 문제이다. 서로 다른 로그가 2종류 이상이어야 한다는 조건은 만족했지만, 첫 이벤트부터 마지막 이벤트까지 555분이 걸려 60분 이내라는 조건을 만족하지 못했다.
- 고칠 파일: correlation.py의 find_chains
- 어떻게 고치나요: 하루의 첫 이벤트와 마지막 이벤트만 비교하는 대신, 60분 이내에 발생한 이벤트들을 별도로 묶을 수 있는지 연결 방식을 검토한다.
- 고친 뒤 확인: 실제로 가까운 시간에 발생한 서로 다른 로그가 연결되는지 확인하고, 관련 없는 이벤트까지 연결되지 않는지도 살펴본다.
- 담당자가 가장 먼저 할 일(선택): seoyeon의 로그인과 다운로드, 서버 접근 기록의 시각을 비교한다.

#### 상황 5 · 협력사 사무실에서 접속한 정상 접속에 알림이 남 (본보기)
- 원인: 규칙 문제입니다. `SaaS 평소와 다른 IP` 규칙은 지난 접속 기록에 없는 IP 이면 모두 알림을 냅니다. 협력사 사무실 IP 203.0.113.80 에서 jiwoo(A4)와 seoyeon(A5)이 출장 · 외근 중에 접속했는데, 조사해 보니 모두 정상 접속이었습니다.
- 고칠 파일: `tuning.py` (`TRUSTED_IPS` 와 `apply_exception`)
- 어떻게 고치나요: 새로 넣고 뺍니다. 믿는 IP 리스트에 `203.0.113.80` 한 개를 넣고, `SaaS 평소와 다른 IP` 규칙의 알림 가운데 그 IP 에서 온 것만 알림 표에서 뺍니다. 다른 규칙의 알림(A3 · A6)은 같은 IP 여도 빼지 않습니다.
- 고친 뒤 확인: 오탐이 4개에서 2개로 줄었는지 보고, 빠진 알림 가운데 진짜 문제(`real` 이 `True`)가 0개인지 봅니다.
- 담당자가 가장 먼저 할 일(선택): 203.0.113.80 이 협력사 사무실 IP 가 맞는지 출장 · 외근 일정과 비교해 확인합니다.

#### 상황 6 · 로그인 규칙이 낸 알림이 평가에서 빠짐 (본보기)
- 원인: 데이터 문제입니다. 로그인 규칙이 낸 알림 A8 은 `login_alerts.json` 에 따로 저장돼 있고, 첫 평가에 쓴 `review_alerts.json` 의 알림 7개에는 들어 있지 않습니다. 평가는 알림 7개만 보고 「알림이 난 진짜 문제」를 세므로, A8 이 가리키는 P4 가 미탐으로 셉니다. 규칙은 알림을 이미 냈지만 평가에 들어가지 못했습니다.
- 고칠 파일: `final_check.py` (`merge_alerts`)
- 어떻게 고치나요: 새로 넣습니다. `pd.concat([alerts, login_alerts])` 로 두 알림 표를 위아래로 이어 붙인 뒤 합친 표로 평가합니다. A8 은 조사해 보니 진짜 문제(`real` 이 `True`)여서 오탐은 늘지 않습니다.
- 고친 뒤 확인: 미탐이 2개(P4 · P5)에서 1개(P5)로 줄고 오탐은 2개 그대로인지 봅니다.
- 담당자가 가장 먼저 할 일(선택): 203.0.113.50 이 로그인에 성공한 뒤 요청한 `/admin` · `/admin/users` 가 모두 403(접근 거부)이었는지, 그 뒤에도 요청이 이어졌는지 로그에서 확인합니다.

#### 상황 7 · 정산 조회 시도에는 알림이 나지 않음
- 원인: 규칙 문제이다. 서버 반복 거절 규칙은 실패가 3번 이상 발생해야 탐지한다. 하지만 seoyeon은 서버 요청이 2번 실패했으므로 권한 없는 정산 조회 요청을 놓쳤다.
- 고칠 파일: access_detection.py의 pick_suspicious, REPEAT_LIMIT 관련 조건
- 어떻게 고치나요: 반복 실패 규칙과 별도로, 정산 정보처럼 중요한 자원에 대한 권한 없는 요청은 한 번만 발생해도 확인하도록 조건을 추가한다.
- 고친 뒤 확인: P5가 탐지되는지 확인하고, 정상적인 업무 요청이 불필요하게 탐지되지 않는지도 확인한다.
- 담당자가 가장 먼저 할 일(선택): seoyeon에게 정산 조회 권한이 있는지와 서버의 거부 사유를 확인한다.

#### 상황 8 · 서버가 같은 네트워크에 열려 있고, 지우면 접속 기록도 사라짐
- 원인: 운영 설정 문제이다. web2의 포트가 모든 네트워크 인터페이스에 바인딩되어 있어 다른 PC에서도 접근할 수 있다. 또한 로그를 컨테이너 안에만 저장하면 컨테이너를 제거할 때 기록을 잃을 수 있다.
- 고칠 파일: compose.secure.yaml의 ports, volumes
- 어떻게 고치나요: web2의 포트를 "8081:80"에서 "127.0.0.1:8081:80"으로 변경한다. 로그를 보관할 서비스에는 ./logs:/var/log/nginx 볼륨을 연결한다.
- 고친 뒤 확인: docker compose ps에서 web2가 127.0.0.1:8081로 표시되는지 확인한다. 로그가 PC의 logs 폴더에 저장되고 컨테이너 종료 후에도 남는지 확인한다.
- 담당자가 가장 먼저 할 일(선택): 외부에 공개할 필요가 없는 서비스의 접속 범위와 로그 보관 상태를 점검한다.
