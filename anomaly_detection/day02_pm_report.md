## 5교시 · 정규화된 이벤트를 표로 읽고 실패만 골라 세기

### 문제 5-1 · 정규화된 이벤트 표를 읽어 실패한 이벤트를 소스별로 세기

- (가) 실행한 출력 전체를 붙여 넣고, 표의 행 수와 열 수, 성공과 실패 개수, 실패한 이벤트의 소스별 개수를 적어 주세요.
  - 쓸 내용: ① 출력 전체(코드 상자에 붙여 넣기) ② 행 수 · 열 수와 성공 · 실패 개수 ③ 소스별 실패 개수
  - 답: ② 행 수 · 열 수와 성공 · 실패 개수 : (57, 7) 성공 34, 실패 23
  ③ 소스별 실패 개수 : web       13
                      server     9
                      saas       1

```
--- 단계 1: 표 크기(행 수, 열 수)와 처음 3개 시각
(57, 7)
2026-11-02 02:14:08
2026-11-02 09:01:05
2026-11-02 09:01:06
--- 단계 2: 성공 · 실패별 개수
result
성공    34
실패    23
Name: count, dtype: int64
--- 단계 3: 실패한 이벤트 23 개의 소스별 개수
source
web       13
server     9
saas       1
Name: count, dtype: int64
--- 단계 4: 전체 이벤트의 소스별 개수
source
web       28
server    15
saas      14
Name: count, dtype: int64
```

- (나) 🔍 실패 개수만 보면 web 이 가장 많습니다. 그렇다면 web 이 가장 문제가 큰 소스라고 말할 수 있을까요? 단계 4의 전체 이벤트 수와 함께 보고 이유를 적어 주세요.
  - 쓸 내용: ① 말할 수 있는지 없는지 ② 소스마다 전체 이벤트 수가 다르다는 것을 근거로 한 이유
  - 답: ① 말할 수 있는지 없는지 : web의 실패 개수가 가장 많다고 해서 가장 문제가 큰 소스라고 단정할 수 없다.
  ② 소스마다 전체 이벤트 수가 다르다는 것을 근거로 한 이유 : web은 전체 28개 중 13개가 실패했고, server는 전체 15개 중 9개, saas는 전체 14개 중 1개가 실패했다. 실패 개수는 web이 가장 많지만 전체 이벤트 수를 기준으로 실패 비율을 계산하면 web은 약 46.4%, server는 60%, saas는 약 7.1%이다. 따라서 실패 비율은 server가 가장 높으므로 실패 개수만으로 어떤 소스가 가장 문제가 많은지 판단하면 안 된다. 또한 실패 원인이 무엇인지에 따라서도 위험성이 달라질 수 있으므로 실제 로그 내용을 추가로 확인해야 한다.

- (다) 🔍 web 이벤트에는 `user` 가 비어 있습니다. 사용자 이름으로 실패를 세려 할 때 web 의 실패 13개는 어떻게 될지 예상하고, 사용자 대신 어떤 열을 보면 같은 대상이 반복했는지 알 수 있을지 이유와 함께 적어 주세요.
  - 쓸 내용: ① 사용자 이름으로 셀 때 web 실패 13개가 어떻게 될지 ② 대신 볼 열과 그 이유
  - 답: ① 사용자 이름으로 셀 때 web 실패 13개가 어떻게 될지 : web 이벤트에는 사용자 이름이 없기 때문에 user 값이 None으로 저장되어 있다. 현재 사용하는 value_counts()는 기본적으로 비어 있는 값을 제외하므로 web의 실패 이벤트 13개는 사용자별 집계에 포함되지 않는다. 만약 비어 있는 값까지 포함해서 집계한다면 사용자 이름이 없는 13개가 하나의 항목으로 묶일 수 있다. 하지만 실제로 모두 같은 사용자의 요청이라는 뜻은 아니다.
  ② 대신 볼 열과 그 이유 : 사용자 이름 대신 ip 열을 확인하면 된다. web 로그에는 사용자 이름은 없지만 접속한 IP 주소는 기록되어 있기 때문이다. 따라서 IP 주소별로 실패 횟수를 세면 같은 주소에서 요청 실패가 반복되었는지 확인할 수 있다. 다만 같은 IP 주소를 여러 사람이 사용할 수도 있으므로 IP가 같다고 반드시 같은 사용자라고 판단해서는 안 된다.

## 6교시 · 실패를 사용자별 · 시간대별로 묶어 세고 저장하기

### 문제 6-1 · 실패한 이벤트를 사용자별 · 시간대별로 묶어 세고 CSV 로 저장하기

- (가) 실행한 출력 전체를 붙여 넣고, 실패가 가장 많은 사용자와 횟수, 실패가 가장 많이 난 시간대와 횟수, 저장된 행 수를 적어 주세요.
  - 쓸 내용: ① 출력 전체(코드 상자에 붙여 넣기) ② 실패가 가장 많은 사용자와 횟수 ③ 가장 많이 난 시간대와 횟수 ④ 저장된 행 수
  - 답: ② 실패가 가장 많은 사용자와 횟수 : dami, 4회
  ③ 가장 많이 난 시간대와 횟수 : 9, 13회
  ④ 저장된 행 수 : 저장된 행 23 개

```
--- 단계 1: 사용자별 실패 횟수
user
dami       4
gaeun      3
seoyeon    2
jiwoo      1
dtype: int64
--- 단계 2: 시간대별 실패 횟수
hour
2      1
9     13
10     3
11     5
18     1
dtype: int64
--- 단계 3: 저장한 파일 failed_events.csv
저장된 행 23 개
```

- (나) 🔍 시간대별 결과에서 실패가 가장 많이 난 시간대의 개수를 보세요. 이 개수는 5교시 단계 3의 어느 소스 개수와 같은가요? 그 실패가 어느 소스에서 났는지 적고(근거는 숫자가 같다는 것까지 쓰면 됩니다), 이어서 확인할 것도 적어 주세요.
  - 쓸 내용: ① 많이 난 실패가 어느 소스에서 난 것인지와 그 근거 ② 이어서 확인할 것
  - 답: ① 많이 난 실패가 어느 소스에서 난 것인지와 그 근거 : 오전 9시대에 실패한 이벤트가 13건으로 가장 많았고, 5교시에서 확인한 web 소스의 실패 개수도 13건이었다. 따라서 web 소스에서 발생한 실패인지 확인할 필요가 있다. 정확하게는 오전 9시대 실패 이벤트의 source 값을 확인하여 실제로 web에서 발생한 것인지 확인해야 한다.
  ② 이어서 확인할 것 : 실패한 요청의 IP 주소와 요청 경로를 확인하여 같은 주소에서 반복적으로 실패했는지 살펴봐야 한다. 또한 raw에 저장된 원본 로그를 확인하여 실제 상태 코드가 401, 403, 404 중 무엇이었는지 확인하고, 짧은 시간 동안 로그인 실패나 특정 경로 접근이 반복되었는지도 살펴봐야 한다.

- (다) 🔍 사용자별 실패 횟수를 모두 더하면 실패한 이벤트 전체보다 적습니다. 몇 개가 모자라고 왜 모자란지 적어 주세요. 그리고 이 차이를 모르고 사용자별 숫자만 보면 어떤 잘못된 판단을 할 수 있을지도 적어 주세요.
  - 쓸 내용: ① 몇 개가 모자란지 ② 모자란 이유 ③ 모르고 넘어가면 생기는 잘못된 판단
  - 답: ① 몇 개가 모자란지 : 사용자별 실패 횟수는 dami 4회, gaeun 3회, seoyeon 2회, jiwoo 1회로 총 10건이다. 전체 실패 이벤트는 23건이므로 13건이 부족하다.
  ② 모자란 이유 : web 로그에는 사용자 이름이 없어 user 값이 None으로 저장되어 있기 때문이다. 현재 코드에서 사용하는 groupby는 기본적으로 사용자 값이 비어 있는 이벤트를 집계에서 제외하므로 web 실패 13건이 사용자별 집계에 포함되지 않았다.
  ③ 모르고 넘어가면 생기는 잘못된 판단 : 사용자별 실패 횟수만 확인하면 전체 실패가 10건이라고 잘못 판단할 수 있다. 또한 사용자 정보가 없는 web 실패 13건을 확인하지 않고 넘어가면서 반복적인 로그인 실패나 의심스러운 접근을 놓칠 수 있다. 따라서 사용자별 집계뿐 아니라 전체 실패 개수와 IP 주소별 실패 횟수도 함께 확인해야 한다.
