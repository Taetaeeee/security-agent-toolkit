## 2교시 · 웹 서버 로그를 공통 이벤트로 바꾸기

### 문제 2-1 · 웹 서버 로그 한 줄을 공통 이벤트로 바꾸기

- (가) 실행한 출력 전체를 붙여 넣고, 정규화한 이벤트 수와 읽기 실패한 줄 수, 성공과 실패 개수를 적어 주세요.
  - 쓸 내용: ① 출력 전체(코드 상자에 붙여 넣기) ② 정규화한 이벤트 수와 읽기 실패한 줄 수 ③ 성공 · 실패 개수
  - 답: ② 정규화한 이벤트 수와 읽기 실패한 줄 수 : 정규화한 이벤트 28 개 · 읽기 실패 2 줄
        ③ 성공 · 실패 개수 : {'성공': 15, '실패': 13}

```
--- 단계 1: 정규화한 이벤트 28 개 · 읽기 실패 2 줄
{'time': '2026-11-02 09:01:05', 'source': 'web', 'user': None, 'ip': '198.51.100.21', 'action': 'GET /', 'result': '성공', 'raw': '198.51.100.21 - - [02/Nov/2026:09:01:05 +0900] "GET / HTTP/1.1" 200 1204 "-" "Mozilla/5.0"'}
--- 단계 2: 처음 나오는 실패 이벤트
{'time': '2026-11-02 09:12:03', 'source': 'web', 'user': None, 'ip': '203.0.113.50', 'action': 'POST /login', 'result': '실패', 'raw': '203.0.113.50 - - [02/Nov/2026:09:12:03 +0900] "POST /login HTTP/1.1" 401 312 "-" "python-requests/2.31.0"'}
--- 단계 3: 성공 · 실패별 개수
{'성공': 15, '실패': 13}
```

- (나) 🔍 시각을 `02/Nov/2026:09:00:00 +0900` 모양 그대로 문자열로 정렬하면 12월 1일 요청(`01/Dec/2026:…`)과 11월 2일 요청(`02/Nov/2026:…`) 중 어느 쪽이 앞에 놓일지 예상하고, 공통 모양(`2026-11-02 09:00:00`)으로 바꾸면 무엇이 달라지는지 이유와 함께 적어 주세요.
  - 쓸 내용: ① 어느 쪽이 앞에 놓일지 ② 공통 모양으로 바꾸면 달라지는 점과 그 이유
  - 답: ① 어느 쪽이 앞에 놓일지 : 12월 1일 요청이 먼저 나온다. 원본 시각을 문자열로 정렬하면 앞에 있는 날짜부터 비교하기 때문에 01로 시작하는 12월 1일이 02로 시작하는 11월 2일보다 먼저 정렬된다.
  ② 공통 모양으로 바꾸면 달라지는 점과 그 이유 : 시각을 2026-11-02 09:00:00처럼 연도, 월, 일, 시각 순서로 변경하면 11월 2일 요청이 12월 1일 요청보다 먼저 정렬된다. 이렇게 공통 모양으로 바꾸면 문자열로 정렬하더라도 날짜와 시간 순서대로 정렬할 수 있다

- (다) 🔍 이벤트에 원래 로그 줄(`raw`)을 그대로 남겨 두는 이유는 무엇인가요? 정규화하면 사라지는 정보를 한 가지 예로 들어 함께 적어 주세요.
  - 쓸 내용: ① `raw` 를 남겨 두는 이유 ② 정규화하면 사라지는 정보의 예
  - 답: ① `raw` 를 남겨 두는 이유 : 정규화하는 과정에서 일부 정보가 사라지거나 잘못 변환될 수 있기 때문에 원본 로그를 다시 확인할 수 있도록 남겨 두는 것이다. 예를 들어 정규화된 결과에서 실패라고 표시되었을 때, 원본 로그를 확인하면 어떤 상태 코드 때문에 실패한 것인지 확인할 수 있다. 또한 정규화한 결과가 잘못되었거나 보안 사고가 발생했을 때 원본 로그와 비교하여 원인을 분석할 수 있다.
  ② 정규화하면 사라지는 정보의 예 : HTTP 상태 코드가 있다. 원본 로그에서는 401, 403, 404처럼 서로 다른 상태 코드를 확인할 수 있지만, 정규화한 이벤트에서는 모두 실패로 표시된다. 따라서 원본 로그를 raw에 보관하면 나중에 실제 상태 코드를 다시 확인할 수 있다.

## 3교시 · 판정 서버 로그와 SaaS 로그를 공통 이벤트로 바꾸기

### 문제 3-1 · 판정 서버 로그와 SaaS 로그를 공통 이벤트로 바꾸기

- (가) 실행한 출력 전체를 붙여 넣고, 판정 서버와 SaaS 이벤트의 수와 성공 · 실패별 개수를 적어 주세요.
  - 쓸 내용: ① 출력 전체(코드 상자에 붙여 넣기) ② 판정 서버 이벤트 수와 성공 · 실패별 개수 ③ SaaS 이벤트 수와 성공 · 실패별 개수
  - 답: ② 판정 서버 이벤트 수와 성공 · 실패별 개수 : {'성공': 6, '실패': 9}
  ③ SaaS 이벤트 수와 성공 · 실패별 개수 : {'실패': 1, '성공': 13}

```
--- 단계 1: 판정 서버 이벤트 15 개
{'성공': 6, '실패': 9}
--- 단계 2: SaaS 이벤트 14 개
{'실패': 1, '성공': 13}
--- 단계 3: 각 로그의 첫 이벤트
{'time': '2026-11-02 09:40:00', 'source': 'server', 'user': 'seoyeon', 'ip': None, 'action': 'SALES:QUERY', 'result': '성공', 'raw': '{"time": "2026-11-02T09:40", "user": "seoyeon", "permission": "SALES:QUERY", "network": "office", "allowed": true, "reason": "역할 권한"}'}
{'time': '2026-11-02 02:14:08', 'source': 'saas', 'user': 'jiwoo', 'ip': '203.0.113.80', 'action': 'login', 'result': '실패', 'raw': {'time': '2026-11-02 02:14:08', 'account': 'jiwoo@a-corp.example', 'event': 'login', 'ip_address': '203.0.113.80', 'outcome': 'failure'}}
```

- (나) 🔍 판정 서버 로그에는 접속 주소가 없어서 `ip` 를 `None` 으로 두었습니다. `None` 대신 가짜 주소 `0.0.0.0` 을 넣으면 주소별로 셀 때 어떤 문제가 생길까요? 이유도 함께 적어 주세요.
  - 쓸 내용: ① 가짜 주소를 넣으면 생기는 문제 ② 그 이유
  - 답: ① 가짜 주소를 넣으면 생기는 문제 : 실제 IP 주소를 알 수 없는 요청들이 모두 0.0.0.0이라는 하나의 주소에서 발생한 것처럼 집계될 수 있다. 따라서 주소별 요청 횟수를 분석할 때 특정 주소에서 요청이 많이 발생한 것으로 잘못 판단할 수 있다.
  ② 그 이유 : None은 IP 주소 정보가 없다는 뜻이지만, 0.0.0.0은 실제로 값이 들어 있는 문자열이기 때문이다. 따라서 프로그램이 이를 하나의 IP 주소로 취급하여 요청 횟수를 집계할 수 있다. 정확한 분석을 위해서는 알 수 없는 정보를 임의의 주소로 채우지 않고 None으로 유지하는 것이 좋다.

- (다) 🔍 정규화하면서 공통 이벤트의 키에 들어가지 않은 정보를 판정 서버 로그에서 찾아 적고, 그 정보를 나중에 어디서 찾을 수 있는지 적어 주세요.
  - 쓸 내용: ① 공통 이벤트의 키에 들어가지 않은 정보 ② 그 정보를 나중에 찾을 수 있는 곳
  - 답: ① 공통 이벤트의 키에 들어가지 않은 정보 : 판정 서버 로그에 있는 network와 reason 정보가 공통 이벤트의 별도 키에는 포함되지 않았다. network는 office나 vpn처럼 접속한 위치를 나타내고, reason은 역할 권한이나 업무 시간 밖처럼 접근이 허용되거나 거부된 이유를 나타낸다.
  ② 그 정보를 나중에 찾을 수 있는 곳 : 정규화된 이벤트의 raw 항목이나 원본 로그 파일인 server_log.jsonl에서 확인할 수 있다. 정규화 과정에서 공통 이벤트의 키에는 포함되지 않았지만, raw에 원래 로그를 그대로 남겨 두었으므로 나중에 접속 위치나 거부 사유를 다시 확인할 수 있다

## 4교시 · 세 로그를 하나로 합쳐 시간순으로 저장하기

### 문제 4-1 · 세 로그의 이벤트를 합쳐 시간순으로 저장하기

- (가) 실행한 출력 전체를 붙여 넣고, 소스별 이벤트 수와 `user` · `ip` 가 비어 있는 이벤트 수, 저장된 이벤트 수를 적어 주세요.
  - 쓸 내용: ① 출력 전체(코드 상자에 붙여 넣기) ② 소스별 이벤트 수 ③ `user` · `ip` 가 비어 있는 이벤트 수 ④ 저장된 이벤트 수
  - 답: ② 소스별 이벤트 수 : {'saas': 14, 'web': 28, 'server': 15}
  ③ `user` · `ip` 가 비어 있는 이벤트 수 : user 가 비어 있는 이벤트 28 개
                                          ip 가 비어 있는 이벤트 15 개
  ④ 저장된 이벤트 수 : 저장된 이벤트 57 개

```
--- 단계 1: 소스별 이벤트 수
{'saas': 14, 'web': 28, 'server': 15}
--- 단계 2: 값이 None 인 이벤트 수
user 가 비어 있는 이벤트 28 개
ip 가 비어 있는 이벤트 15 개
--- 단계 3: gaeun 의 이벤트를 시간순으로
2026-11-02 10:05:00 server ACCOUNT:CHANGE 실패
2026-11-02 10:09:00 server ACCOUNT:CHANGE 실패
2026-11-02 10:12:55 saas login 성공
2026-11-02 10:14:00 server ACCOUNT:CHANGE 실패
2026-11-02 16:10:00 server SALES:QUERY 성공
--- 단계 4: 저장한 파일 normalized_events.json
저장된 이벤트 57 개
```

- (나) 🔍 단계 3의 gaeun 이벤트를 시간순으로 보고, 서로 다른 소스에서 나온 이벤트가 어떻게 이어지는지 적고, 로그를 따로 볼 때와 무엇이 달라지는지 적어 주세요.
  - 쓸 내용: ① 여러 소스에 걸친 이벤트의 순서 ② 로그를 따로 볼 때와 달라지는 점
  - 답: ① 여러 소스에 걸친 이벤트의 순서 : gaeun은 판정 서버에서 ACCOUNT 요청이 2번 실패한 뒤, SaaS에서 로그인에 성공했다.이후 다시 판정 서버에서 ACCOUNT 요청이 1번 실패했고, 오후에는 SALES 요청에 성공했다.
  따라서 계정 변경 실패 2회 → SaaS 로그인 성공 → 계정 변경 실패 1회 → 영업 조회 성공 순서로 확인할 수 있다.
  ② 로그를 따로 볼 때와 달라지는 점 : 회로그를 따로 보면 판정 서버에서 계정 변경을 여러 번 실패한 기록과 SaaS에서 로그인에 성공한 기록을 각각 확인해야 한다. 하지만 여러 로그를 합쳐 시간순으로 정렬하면 같은 사용자가 서로 다른 서비스에서 어떤 요청을 했는지 한 번에 확인할 수 있다. 특히 계정 변경 요청이 반복해서 거부되는 사이에 SaaS 로그인이 성공했다는 사실을 알 수 있어, 사용자의 행동을 전체적인 흐름으로 분석하기 쉬워진다. 다만 이 기록만으로 비정상적인 행동이라고 확정할 수는 없으므로 각 요청의 거부 사유와 실제 업무 여부를 추가로 확인해야 한다.

- (다) 🔍 `user` 가 비어 있는 이벤트가 28개입니다. 어느 로그(소스)의 이벤트이고 왜 비어 있는지 적어 주세요. 그리고 사용자 이름별로 개수를 세면 이 28개가 어떻게 될지 예상해 적어 주세요.
  - 쓸 내용: ① 비어 있는 이벤트의 로그(소스)와 이유 ② 사용자 이름별로 셀 때의 예상
  - 답: ① 비어 있는 이벤트의 로그(소스)와 이유 : user가 비어 있는 이벤트 28개는 웹 서버(web) 로그에서 나온 것이다. 웹 서버 로그에는 접속한 IP 주소와 요청 경로, 상태 코드 등은 있지만 실제 사용자 이름은 기록되어 있지 않기 때문이다. 따라서 정규화할 때 사용자 이름을 알 수 없어 user를 None으로 저장한다.
  ② 사용자 이름별로 셀 때의 예상 : 사용자 이름을 기준으로 개수를 세면 user가 None인 이벤트 28개가 하나의 항목으로 묶일 수 있다. 하지만 실제로는 서로 다른 사용자가 요청했을 가능성이 있으므로, None으로 묶인 28개를 모두 같은 사용자의 요청이라고 판단해서는 안 된다. 또한 None 값을 제외하고 집계하도록 만들었다면 이 28개는 사용자별 집계에서 빠지게 된다. 따라서 정확한 사용자별 분석을 위해서는 로그인 기록 등 다른 로그와 비교하여 사용자 정보를 추가로 확인해야 한다.
