### 문제 2-1 · 서버가 거절한 요청 중 반복된 것을 찾고 이유로 순서 정하기

- (가) 실행한 출력 전체를 붙여 넣고, 서버 실패 수와 먼저 확인할 이벤트 수, 1순위 사용자를 적어 주세요.
  - 쓸 내용: ① 출력 전체(코드 상자에 붙여 넣기) ② 서버 실패 수 ③ 먼저 확인할 이벤트 수 ④ 1순위 사용자
  - 답: ② 서버 실패 수 9 개
  ③ 먼저 확인할 이벤트 수 7 개
  ④ 1순위 사용자 dami

```
--- 단계 1: 판정 서버의 실패 이벤트 9 개
--- 단계 2: 먼저 확인할 실패 이벤트 7 개
--- 단계 3: 우선순위
1 퇴사한 계정 dami SALES:QUERY 2026-11-02 11:02:00
1 퇴사한 계정 dami SALES:QUERY 2026-11-02 11:03:00
1 퇴사한 계정 dami SALES:CHANGE 2026-11-02 11:05:00
1 퇴사한 계정 dami SALES:QUERY 2026-11-02 11:08:00

3 규칙은 허용인데 서버가 거절 gaeun ACCOUNT:CHANGE 2026-11-02 10:14:00
```

- (나) 🔍 ① dami 의 실패 4개는 3과목(접근통제) 규칙으로 어떤 이유로 판정됐고, 왜 1순위일까요? ② gaeun 의 실패 3개는 규칙으로는 「허용」인데 서버가 거절했습니다. 공격이라고 확정할 수 있는지 적고, 먼저 무엇을 확인해야 하는지 적어 주세요.
  - 쓸 내용: ① dami 의 판정 이유와 1순위인 까닭 ② 공격이라고 확정할 수 있는지와 먼저 확인할 것
  - 답:  ① dami 의 판정 이유와 1순위인 까닭 : dami는 퇴사한 계정이기 때문에 접근통제 규칙에서 '퇴사한 계정'으로 판정되었다. 퇴사한 계정인데도 영업 조회와 변경 요청이 4번 발생했으므로 계정이 정상적으로 비활성화되었는지, 누가 접근을 시도했는지 우선 확인할 필요가 있다. 따라서 퇴사한 계정에 대한 반복적인 접근이므로 1순위로 확인해야 한다.
  ② 공격이라고 확정할 수 있는지와 먼저 확인할 것 : 공격이라고 확정할 수 없다. gaeun은 ACCOUNT 요청이 3번 실패했지만, 접근통제 규칙으로 다시 확인했을 때는 허용으로 판정되었다. 따라서 실제 서버에서 거부된 이유를 먼저 확인해야 한다. 원본 로그의 거부 사유와 접속 네트워크, 요청 시각을 확인하고, 서버에 적용된 접근통제 조건과 차이가 있는지 살펴봐야 한다. 정상적인 사용자가 접속 조건 때문에 거부되었을 수도 있으므로 반복 실패만으로 공격이라고 판단해서는 안 된다.

- (다) 🔍 seoyeon 의 서버 실패 2건(11:40 `SETTLE:QUERY` · 18:20 `SALES:CHANGE`)은 먼저 확인할 이벤트에 들어가지 않았습니다. 들어가지 않은 이유를 오늘 규칙(실패 3번 이상)으로 설명하고, 이 규칙 때문에 놓칠 수 있는 경우를 한 가지 적어 주세요.
  - 쓸 내용: ① 먼저 확인할 이벤트에 들어가지 않은 이유 ② 이 규칙이 놓칠 수 있는 경우 한 가지
  - 답: ① 먼저 확인할 이벤트에 들어가지 않은 이유 : 현재 규칙은 같은 사용자의 실패가 3번 이상 발생해야 먼저 확인할 이벤트로 분류한다. seoyeon은 SETTLE와 SALES 요청이 각각 1번씩 실패하여 총 2번이므로 기준에 미치지 않아 제외되었다.
  ② 이 규칙이 놓칠 수 있는 경우 한 가지 : 접근 시도가 1~2번만 발생했더라도 중요한 정보나 민감한 권한에 접근하려는 요청일 수 있다. 하지만 현재 규칙은 실패 횟수만 기준으로 판단하므로 이러한 요청을 놓칠 수 있다. 따라서 반복 횟수뿐 아니라 어떤 권한에 접근했는지와 거부 사유도 함께 확인해야 한다.

## 3교시 · SaaS 로그에서 이상 사용 세 가지 찾기

### 문제 3-1 · SaaS 로그에서 이상 사용 세 가지 찾기

- (가) 실행한 출력 전체를 붙여 넣고, 규칙마다 해당한 사용자를 적어 주세요.
  - 쓸 내용: ① 출력 전체(코드 상자에 붙여 넣기) ② 업무 시간 밖 로그인 사용자 ③ 평소와 다른 IP 사용자 ④ 대량 다운로드 사용자
  - 답: ② 업무 시간 밖 로그인 사용자 : jiwoo
  ③ 평소와 다른 IP 사용자 : 'jiwoo', 'seoyeon'
  ④ 대량 다운로드 사용자 : 'seoyeon'

```
--- 단계 1: 업무 시간 밖 로그인 1 건
                  time source   user            ip action result
0  2026-11-02 02:14:08   saas  jiwoo  203.0.113.80  login     실패
--- 단계 2: 평소와 다른 IP 로 로그인한 사용자 ['jiwoo', 'seoyeon']
--- 단계 3: 파일을 5번 이상 내려받은 사용자 ['seoyeon']
```

- (나) 🔍 jiwoo 는 업무 시간 밖(02:14)과 평소와 다른 IP 두 규칙에 해당하지만 그 로그인은 실패였습니다. 이 기록만으로 계정 도용을 확정할 수 있나요? 그렇게 판단한 이유와, 샘플 로그에서 더 찾아볼 수 있는 것을 한 가지 적어 주세요.
  - 쓸 내용: ① 도용이라고 확정할 수 있는지 없는지 ② 더 확인할 정보 한 가지
  - 답: ① 도용이라고 확정할 수 있는지 없는지 : 계정 도용이라고 확정할 수 없다. jiwoo가 새벽 2시 14분에 평소와 다른 IP에서 로그인을 시도했지만 실패했기 때문이다. 정상적인 사용자가 평소와 다른 장소나 컴퓨터에서 접속을 시도했을 가능성도 있으므로, 이 기록만으로 다른 사람이 계정을 사용하려 했다고 판단하기는 어렵다.
  ② 더 확인할 정보 한 가지 : 샘플 로그에서 jiwoo의 다른 로그인 기록을 찾아 실제로 로그인에 성공한 기록이 있는지 확인한다. 다른 시간대의 로그인 기록과 IP 주소를 비교하면 평소와 다른 접속이 반복되었는지 확인할 수 있다.

- (다) 🔍 gaeun 은 평소 IP 기록이 없어 「평소와 다른 IP」 규칙에서 제외됩니다. 제외하지 않으면 어떤 일이 생기고, 제외하면 어떤 위험이 남나요?
  - 쓸 내용: ① 제외하지 않을 때 생기는 일 ② 제외했을 때 남는 위험
  - 답: ① 제외하지 않을 때 생기는 일 : gaeun은 평소 IP 기록이 없기 때문에 usual_ip가 None으로 저장된다. 이 상태에서 현재 접속한 IP와 비교하면 실제 IP가 None과 다르므로 평소와 다른 IP로 판단될 수 있다. 따라서 평소 기록이 없는 사용자까지 모두 새로운 IP에서 접속한 것으로 잘못 탐지하여 불필요한 알림이 발생할 수 있다.
  ② 제외했을 때 남는 위험 : 평소 IP 기록이 없다는 이유로 검사에서 제외하면 실제로 평소와 다른 환경에서 접속한 경우에도 탐지하지 못할 수 있다. 특히 다른 사람이 해당 계정으로 로그인을 시도해도 평소 IP와 비교할 기준이 없으므로 이상 접속 여부를 판단하기 어렵다. 따라서 평소 기록이 없는 사용자는 별도로 관리하고, 로그인 기록을 쌓아 비교 기준을 만드는 것이 필요하다.

## 4교시 · 웹 실패 로그에서 경로를 스캔한 IP 찾기

### 문제 4-1 · 웹 실패 로그에서 경로를 스캔한 IP 찾기

- (가) 실행한 출력 전체를 붙여 넣고, 스캔으로 본 IP 와 이유를 적어 주세요.
  - 쓸 내용: ① 출력 전체(코드 상자에 붙여 넣기) ② 스캔으로 본 IP ③ 이유
  - 답: ② 스캔으로 본 IP : '198.51.100.90'
  ③ 이유 : '스캐너 경로를 3번 요청'

```
--- 단계 1: 웹 서버의 실패 이벤트 13 개
--- 단계 2: 스캐너 경로를 요청한 IP 와 횟수
ip
198.51.100.90    3
Name: count, dtype: int64
--- 단계 3: 스캔으로 본 IP 와 이유
{'ip': '198.51.100.90', 'reason': '스캐너 경로를 3번 요청'}
--- 단계 4: 스캐너 경로가 없어 제외한 IP
203.0.113.50
198.51.100.21
198.51.100.34
198.51.100.77
```

- (나) 🔍 203.0.113.50 은 실패한 요청이 7번 있지만 스캔에서 제외됐습니다. 제외된 이유와, 제외하지 않으면 담당자에게 어떤 일이 생기는지 적어 주세요.
  - 쓸 내용: ① 제외된 이유 ② 제외하지 않을 때 생기는 일
  - 답: ① 제외된 이유 : 203.0.113.50은 로그인 실패 5번과 관리자 경로 접근 실패 2번으로 총 7번의 실패가 발생했다. 하지만 이번 규칙에서 확인하는 /.env, /wp-login, /phpmyadmin 경로에 접근한 기록이 없기 때문에 스캔 IP에서 제외되었다.
  ② 제외하지 않을 때 생기는 일 : 스캐너 경로에 접근하지 않았는데도 실패 횟수가 많다는 이유로 경로 스캔이라고 잘못 판단할 수 있다. 이렇게 되면 담당자가 로그인 실패와 경로 스캔을 구분하기 어려워지고, 실제로 어떤 문제가 발생했는지 확인하는 데 혼란이 생길 수 있다. 따라서 경로 스캔 규칙에서는 해당 경로를 요청했는지 확인하고, 로그인 실패는 별도의 규칙으로 조사하는 것이 좋다.

- (다) 🔍 198.51.100.21 의 `GET /board/99` 실패 1건은 이 규칙에서 어떤 조건 때문에 제외되나요? 그리고 해킹 도구가 `SCANNER_PATTERN` 에 없는 경로(예: `/backup.zip`)를 요청하면 이 규칙이 탐지하지 못한다는 점을 설명해 주세요.
  - 쓸 내용: ① 한 번의 실패가 제외되는 과정 ② 목록에 없는 경로를 요청하면 탐지하지 못한다는 점
  - 답: ① 한 번의 실패가 제외되는 과정 : 198.51.100.21의 GET /board/99 요청은 404로 실패했기 때문에 웹 실패 이벤트에는 포함된다. 하지만 스캐너 경로로 정한 /.env, /wp-login, /phpmyadmin 중 어느 것에도 해당하지 않으므로 스캔 IP 집계에서는 제외된다. 따라서 실패가 한 번이라서 제외된 것이 아니라 스캐너 패턴에 해당하지 않아서 제외된 것이다.
  ② 목록에 없는 경로를 요청하면 탐지하지 못한다는 점 : 현재 규칙은 SCANNER_PATTERN에 등록된 경로가 포함되어 있는지만 확인한다. 따라서 해킹 도구가 /backup.zip처럼 목록에 없는 경로를 요청하면 실제로 의심스러운 접근이더라도 스캔으로 탐지하지 못한다. 이런 문제를 줄이려면 새로운 스캔 경로를 확인하여 패턴을 보완하고, 요청 횟수나 짧은 시간에 여러 경로를 탐색하는 행동도 함께 확인할 필요가 있다.
