## 5교시 · 어제 명령 복습 · 서버 두 대 켜고 접속 기록 구분해 읽기

### 문제 5-1 · 어제와 같은 명령으로 서버 두 대를 켜고 접속 기록을 구분해 읽기

- (가) 내가 `web-three` 와 `web-four` 를 켠 `docker run` 명령 두 개를 붙여 넣어 주세요.
  - 쓸 내용: 윈도는 `MSYS_NO_PATHCONV=1` 부터, 맥북은 `docker run` 부터 친 그대로 두 줄
  - 답:

```
MSYS_NO_PATHCONV=1 docker run -d --name web-three -p 8082:80 -v "$(pwd)/site-three:/usr/share/nginx/html:ro" nginx:1.28
MSYS_NO_PATHCONV=1 docker run -d --name web-four -p 8083:80 -v "$(pwd)/site-four:/usr/share/nginx/html:ro" nginx:1.28
```

- (나) 🔍 `docker ps` 에서 `web-three` 와 `web-four` 줄의 `PORTS` 값을 각각 적어 주세요.
  - 쓸 내용: 「web-three: … / web-four: …」
  - 답: web-three: 0.0.0.0:8082->80/tcp
        web-four: 0.0.0.0:8083->80/tcp
- (다) 🔍 8082 로 세 번, 8083 으로 한 번 접속했을 때 `docker logs web-three` 와 `docker logs web-four` 의 `"GET / HTTP/1.1"` 줄은 각각 몇 개였고, 왜 그렇게 나뉘나요?
  - 쓸 내용: ① web-three 의 줄 수 ② web-four 의 줄 수 ③ 그렇게 나뉘는 이유(어느 포트로 온 요청이 어느 서버에 기록되는지)
  - 답: web-three 의 줄 수 : 3줄, web-four 의 줄 수 : 1줄
        그렇게 나뉘는 이유 : PC의 8082번 포트로 들어온 요청은 web-three 컨테이너의 80번 포트로 전달되고, 8083번 포트로 들어온 요청은 web-four 컨테이너의 80번 포트로 전달된다. 따라서 8082로 세 번 접속한 기록은 web-three에 3줄, 8083으로 한 번 접속한 기록은 web-four에 1줄 남는다.
- (라) 🔍 `stop` 뒤에 `docker ps` 와 `docker ps -a` 에서 두 서버가 각각 어떻게 보였고, `rm` 뒤에는 어떻게 되었나요?
  - 쓸 내용: 「stop 뒤 ps: … / stop 뒤 ps -a: … / rm 뒤 ps -a: …」
  - 답: stop 뒤 ps: web-three와 web-four가 실행 중인 컨테이너 목록에서 사라졌다.
        stop 뒤 ps -a: web-three와 web-four이 Exited(0)으로 남아있음
        rm 뒤 ps -a: web-three와 web-four가 삭제되어 목록에 더 이상 표시되지 않았다.
- (한 줄) 보안 담당에게 보낼 답을 한 문장으로 적어 주세요.
  - 쓸 내용: 보안 담당이 바로 읽을 수 있는 한 문장(서버를 몇 대 어떻게 켰고 기록이 어떻게 남았는지)
  - 답: Nginx 컨테이너 두 대를 각각 8082번과 8083번 포트로 실행한 결과, web-three에는 접속 기록 3건, web-four에는 1건이 별도로 남는 것을 확인했으며 테스트 후 두 컨테이너를 정상 종료하고 삭제했습니다.
- 이 교시에서 새로 알게 된 것 하나를 적어 주세요.
  - 쓸 내용: 자유롭게
  - 답: Docker에서는 같은 Nginx 이미지를 사용하더라도 컨테이너마다 다른 외부 포트를 연결하여 여러 웹 서버를 동시에 실행할 수 있다는 것을 새로 알게 되었다. 특히 두 컨테이너 모두 내부에서는 80번 포트를 사용하지만 외부에서는 8082번과 8083번으로 구분되며, 각 서버의 접속 기록도 별도로 남는다는 점이 기억에 남았다. 또한 docker stop은 컨테이너를 종료하는 명령이고 docker rm은 종료된 컨테이너를 삭제하는 명령이라는 차이도 알게 되었다.

## 6교시 · 내 이미지 만들기 (Dockerfile)

### 문제 6-1 · Dockerfile 두 줄을 써서 내 이미지 만들기

- (가) 내가 쓴 Dockerfile 두 줄을 붙여 넣어 주세요.
  - 쓸 내용: Dockerfile 두 줄(`FROM` 줄 · `COPY` 줄)
  - 답:

```
FROM nginx:1.28
COPY site-three/index.html /usr/share/nginx/html/index.html
```

- (나) 🔍 `FROM` 과 `COPY` 가 각각 하는 일을 적어 주세요.
  - 쓸 내용: ① FROM 이 하는 일 ② COPY 가 하는 일
  - 답: FROM이 하는 일 : 새 이미지에 포함할 기존 이미지를 정한다. 새 이미지에는 이 이미지의 내용이 모두 들어간다.
    COPY가 하는 일 : 내 PC의 파일을 이미지 안의 지정한 경로에 복사한다.
- (다) 🔍 5교시와 달리 `docker run` 에 `-v` 가 없는데도 내 화면이 나오는 이유는 무엇인가요?
  - 쓸 내용: ① 어제 파일이 컨테이너에 닿던 방법 ② 오늘 파일이 서버에 있는 위치와 시점
  - 답: 5교시에는 `docker run`에서 `-v` 옵션을 사용하여 PC의 폴더를 실행 중인 컨테이너에 연결했으므로, 해당 폴더가 없으면 내 페이지를 사용할 수 없었다.
  반면 6교시에는 `docker build` 과정에서 Dockerfile의 `COPY` 명령으로 `site-three/index.html` 파일을 이미지 내부의 `/usr/share/nginx/html/index.html`에 복사했다.
  따라서 컨테이너를 실행할 때 별도의 `-v` 옵션 없이도 이미지에 포함된 파일을 Nginx가 제공하여 같은 화면이 나타난다.
- (라) 🔍 `docker build` 출력에서 `[2/2] COPY` 줄과 `naming to` 줄을 붙여 넣고, 각각 무엇을 알려 주는지 적어 주세요.
  - 쓸 내용: ① 두 줄 ② 각 줄이 알려 주는 것
  - 답: `[2/2] COPY` 줄 : Dockerfile 둘째 줄을 처리한 단계이다. 이 줄이 있으면 내 파일이 이미지 안에 들어간 것이다.
    `naming to` 줄 : 완성한 이미지에 내가 정한 이름을 붙였다는 뜻이다. 이 줄이 있어야 다음 docker run에 이름을 쓸 수 있다.

```
[2/2] COPY site-three/index.html /usr/share/nginx/html/index.html
naming to docker.io/library/my-nginx:1
```


## 7교시 · 이미지 버전 다루기 · 되돌리기 · 정리 · 올리기

### 문제 7-1 · 파일을 고쳐 보고, 이미지를 다시 만들어 반영하기

- (가) 파일을 고친 직후 새로 고침했을 때 화면에 무엇이 나왔나요?
  - 쓸 내용: 새로 고침했을 때 보인 화면의 큰 제목
  - 답: site-three
- (나) 🔍 파일을 고쳤는데도 화면이 바뀌지 않은 이유와, 바꾸려면 무엇을 해야 하는지 적어 주세요.
  - 쓸 내용: ① 바뀌지 않은 이유(서버가 보는 파일이 어디 있는지) ② 바꾸려면 할 일
  - 답: 서버가 사용하는 파일은 기존 이미지 `my-nginx:1`에 복사되어 있기 때문에 PC의 원본 파일을 수정해도 실행 중인 컨테이너에는 자동으로 반영되지 않는다.
  변경 내용을 반영하려면 `docker build -t my-nginx:2 .` 명령으로 새 이미지를 만든 다음, 기존 `my-site` 컨테이너를 삭제하고 새 이미지 `my-nginx:2`로 컨테이너를 다시 생성해야 한다.
- (다) 🔍 5교시의 `-v` 방식과 6교시의 이미지에 넣는 방식은 파일을 고쳤을 때 반영되는 방법이 어떻게 다른가요?
  - 쓸 내용: ① -v 방식의 반영 방법 ② 이미지에 넣는 방식의 반영 방법
  - 답: `-v` 방식은 PC의 폴더를 컨테이너에 직접 연결하기 때문에 파일을 수정하면 일반적으로 브라우저 새로 고침만으로 변경 내용이 반영된다.
  이미지에 파일을 넣는 방식은 `docker build` 과정에서 파일이 이미지 안에 복사되므로 PC의 원본을 수정해도 기존 이미지에는 반영되지 않는다. 따라서 수정된 파일로 새 이미지를 빌드하고, 기존 컨테이너를 삭제한 뒤 새 이미지로 다시 실행해야 한다.

### 문제 7-2 · 이전 버전으로 되돌리고 쓰지 않는 이미지 지우기

- (가) 이전 버전으로 되돌린 뒤 `docker ps` 의 `IMAGE` 칸 값과 브라우저에 나온 제목을 적어 주세요.
  - 쓸 내용: 「IMAGE: … / 브라우저 제목: …」
  - 답: IMAGE: my-nginx:1, 브라우저 제목: site-three
- (나) 🔍 쓰고 있는 `my-nginx:1` 을 `docker rmi` 로 지우려 했을 때 에러 문구의 핵심과, 어떻게 해결했는지 적어 주세요.
  - 쓸 내용: ① 에러 문구의 핵심 ② 지워지지 않은 이유 ③ 해결한 순서
  - 답: Error response from daemon: conflict: unable to delete my-nginx:1 (must be forced) - container 91f7d3bcee6b is using its referenced image 16428506cff4
  지워지지 않은 이유: my-site 컨테이너가 my-nginx:1 이미지를 사용하고 있기 때문이다.
  먼저 사용하지 않는 my-nginx:2 이미지를 docker rmi my-nginx:2로 삭제한다. 이후 docker rm -f my-site로 my-nginx:1을 사용하는 컨테이너를 삭제하고 docker ps -a로 확인한 다음, docker rmi my-nginx:1로 남은 이미지를 삭제한다.
- (다) 🔍 이미지에 `:1` · `:2` 같은 태그를 붙여 두면 문제가 생겼을 때 어떤 점이 좋은가요?
  - 쓸 내용: ① 되돌리는 방법 ② 어느 버전이 켜져 있는지 아는 방법
  - 답: 이미지에 `:1`, `:2`처럼 버전별 태그를 붙여 두면 새 버전에 문제가 생겼을 때 기존 이미지를 다시 빌드하지 않고 이전 버전으로 되돌릴 수 있다.
  되돌리는 방법은 `docker rm -f my-site`로 v2 컨테이너를 삭제한 후, `docker run -d --name my-site -p 8090:80 my-nginx:1`로 이전 버전의 컨테이너를 다시 실행하는 것이다.
  현재 어느 버전이 실행 중인지는 `docker ps` 명령의 IMAGE 열에서 확인할 수 있다.
- (한 줄) 보안 담당에게 보낼 답을 한 문장으로 적어 주세요.
  - 쓸 내용: 보안 담당이 바로 읽을 수 있는 한 문장(되돌린 일과 정리한 일)
  - 답: 수정된 안내 페이지를 `my-nginx:2` 이미지로 빌드해 반영한 뒤, 기존 `my-nginx:1` 이미지로 컨테이너를 다시 실행하여 이전 화면으로 복구했으며, 사용하지 않는 v2 이미지와 테스트가 끝난 컨테이너 및 이미지를 정리했습니다.
- 이 교시에서 새로 알게 된 것 하나를 적어 주세요.
  - 쓸 내용: 자유롭게
  - 답: Docker 이미지에 파일을 포함하는 방식은 PC의 파일을 수정해도 기존 이미지가 자동으로 바뀌지 않기 때문에 새 이미지를 빌드하고 컨테이너를 다시 생성해야 한다는 것을 알게 되었다. 또한 이미지에 버전별 태그를 붙여 두면 새 버전에 문제가 생겼을 때 이전 이미지를 다시 빌드하지 않고도 복구할 수 있다는 점을 새로 알게 되었다. `docker rm`은 컨테이너 삭제, `docker rmi`는 이미지 삭제라는 차이도 알게 되었다.

  - 쓸 내용: ① 빨간 목록의 줄 수 ② .env · .venv 가 있었는지
  - 답: 11개, 없음
