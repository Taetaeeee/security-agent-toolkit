### 문제 2-1 · 새벽 대량 조회 사건 추적하고 단정할 수 있는지 따지기

- (가) 의심스러운 접근 기록은 몇 번이고, 이상해 보이지만 정상인 줄은 몇 번인가요? 한 줄씩은 정상 같지만 모아서 보면 이상한 줄이 있으면 함께 적어 주세요.
  - 쓸 내용: 「의심: 번호 … / 이상해 보이지만 정상: 번호 … (정상으로 본 이유) / 모으면 이상한 줄: 번호 … (이유)」
  - 답: 의심: 2 3 4 5, 새벽에 seoyeon 계정이 미등록 기기에서 비밀번호만으로 로그인한 후 담당 자원이 아닌 SETTLE을 120건 조회했다.

  - 쓸 내용: 근거 필드 세 가지 이상, 필드마다 「어떤 값이 어떤 값과 다른지」
  - 답: 의심스러운 근거 필드는 시각, 기기, 출발 IP, 로그인 방식, 자원, 조회 건수이다.

    seoyeon 계정의 평소 접속은 등록 기기 NB-0417과 IP 10.20.4.21을 사용했지만, 2번은 새벽 02:14에 미등록 기기 NB-7741과 다른 사내 IP 10.20.5.77에서 로그인했다. 또한 평소 로그인은 비밀번호와 MFA를 모두 사용했지만 2번은 비밀번호만으로 성공했다.

    seoyeon의 담당 자원은 SALES인데 3~5번에서 SETTLE을 40건씩 총 120건 조회했다. 12·14~17번도 SETTLE을 19건씩 총 95건 반복 조회했으므로 정상적인 업무인지 추가 확인이 필요하다.
- (다) 🔍 방화벽이 막지 못하고 통과한 이유를 5대 원칙의 어느 칸이 비어 있었는지로 설명해 주세요.
  - 쓸 내용: ① 비어 있던 칸 두 개 이상 ② 칸마다 확인했어야 할 것
  - 답: ID, Device, Application, Policy 항목의 통제가 부족했을 가능성이 있다.

    ID에서는 비밀번호만으로 로그인한 사용자가 실제 seoyeon인지 MFA로 추가 확인했어야 한다. Device에서는 NB-7741이 회사에 등록된 기기인지 확인했어야 한다. Application에서는 영업팀 계정이 담당하지 않는 SETTLE 자원을 조회할 권한이 있는지 검사했어야 한다. Policy에서는 새벽 로그인과 대량·반복 조회를 이상 행동으로 판단하여 추가 인증이나 경보를 적용했어야 한다.

    방화벽이 통신을 허용했더라도 사용자 신원, 기기 상태, 애플리케이션 권한, 접속 상황까지 정상이라고 보장되는 것은 아니다.
- (라) 🔍 이 기록만으로 「seoyeon 계정이 도용됐다」고 단정할 수 있나요? 기록으로 확인된 것과 확인하지 못한 것, 그것을 확인하려면 볼 자료를 적어 주세요.
  - 쓸 내용: ① 단정할 수 있는지 ② 기록으로 확인된 것 ③ 확인하지 못한 것 ④ 확인하려면 볼 자료
  - 답: 이 기록만으로 seoyeon 계정이 도용되었다고 단정할 수 없다.

    확인된 것은 새벽 02:14에 미등록 기기 NB-7741에서 비밀번호만으로 로그인이 성공했고, 이후 담당 자원이 아닌 SETTLE을 120건 조회했다는 사실이다. 또한 낮에도 SETTLE을 95건 반복 조회한 기록이 확인된다.

    하지만 실제 접속자가 seoyeon 본인인지, 해당 기기가 승인된 기기인지, 조회가 정상 업무였는지, 실제 자료 유출이 발생했는지는 확인되지 않았다.

    이를 확인하기 위해 VPN·로그인 및 MFA 인증 기록, 기기 등록 기록, 애플리케이션 접근 권한과 조회 감사 로그, 담당자의 업무 승인 내역을 확인해야 한다.
- (한 줄) 보안 담당에게 보낼 답을 한 문장으로 적어 주세요.
  - 쓸 내용: 보안 담당이 바로 읽을 수 있는 한 문장(무슨 일이 있었고 무엇을 더 확인해야 하는지)
  - 답: seoyeon 계정에서 새벽에 미등록 기기로 비밀번호만 사용한 로그인과 담당 외 정산 자료 120건 조회, 낮 시간의 반복 조회 95건이 확인되어 계정 도용 가능성을 조사 중이며 인증·기기·권한·자료 접근 기록을 추가 확인해야 합니다.

### 문제 2-2 · 접속 요청 여섯 개를 5대 원칙의 칸으로 분류하기

- (가) 요청 ① ~ ⑥ 은 각각 5대 원칙 중 어느 칸에서 걸리나요? 걸리지 않고 통과하면 「통과」라고 적어 주세요.
  - 쓸 내용: 「①: … / ②: … / ③: … / ④: … / ⑤: … / ⑥: …」 여섯 개
  - 답: 
    ①: ID
    ②: Device
    ③: Application
    ④: Network
    ⑤: Policy
    ⑥: 통과
- (나) 🔍 요청 ⑤ 는 ID · Device · Application 이 모두 정상인데 왜 Policy 칸에서 걸리나요?
  - 쓸 내용: ① 정상인 것 ② 평소와 달라진 상황 ③ Policy 칸이 하는 일
  - 답: 요청 ⑤는 비밀번호와 MFA 인증(ID), 회사 노트북의 보안 상태(Device), 영업 앱 접근 권한(Application)이 모두 정상이다. 하지만 평소 서울에서 접속하던 사용자가 해외 IP로 새벽 03:00에 접속했다는 점이 다르다. Policy는 접속 시간, 위치, 위험도에 따라 추가 인증이나 접근 제한을 적용하는 역할을 하므로 이 요청은 Policy에서 걸린다.
- (다) 요청 ③ 과 ④ 는 둘 다 가면 안 되는 곳에 닿으려는 시도인데 왜 서로 다른 칸에서 걸리나요?
  - 쓸 내용: ① ③ 이 확인하는 것 ② ④ 가 확인하는 것
  - 답: ③은 마케팅팀 직원이 권한이 없는 인사 시스템 앱에 접근하려는 요청이므로, 해당 애플리케이션을 사용할 권한이 있는지 확인하는 Application에서 걸린다.

  ④는 개발팀 직원이 앱을 거치지 않고 서버 구역의 DB에 직접 연결하려는 요청이므로, 허용된 네트워크 구역과 자원에만 접근하도록 제한하는 Network에서 걸린다.
- 이 교시에서 새로 알게 된 것 하나를 적어 주세요.
  - 쓸 내용: 자유롭게
  - 답: Zero Trust는 로그인에 성공했다고 해서 모든 접근을 허용하는 것이 아니라 ID, Device, Network, Application, Policy의 다섯 가지 항목을 각각 확인한다는 것을 새로 알게 되었다. 특히 애플리케이션의 사용 권한을 확인하는 것과 네트워크 구역에 대한 접근을 제한하는 것이 서로 다른 보안 원칙이라는 점이 기억에 남았다. 또한 정상적으로 인증된 사용자라도 평소와 다른 시간이나 위치에서 접속하면 추가 확인이 필요하다는 것을 알게 되었다.

### 문제 3-1 · 권한 변경 판단 함수의 점수 직접 정하기

- (가) 내가 채운 코드 여덟 줄을 붙여 넣어 주세요.
  - 쓸 내용: `# ←` 여덟 곳에 채운 코드(점수 세 개 · 역할 검사 두 줄 · MFA 점수 블록 세 줄)
  - 답:

```
HEALTH_POINTS = 40
MFA_POINTS = 20
COUNTRY_POINTS = 30
if account["role"] != "account_admin":
        return "거부", ["관리자 역할이 아님"]
if req["mfa"] == False:
        score+=MFA_POINTS
        reasons.append("MFA 안 함")
```

- (나) 🔍 실행해서 나온 요청 A ~ F 의 결정을 적어 주세요. 모두 기대 결정과 같은지도 함께 적어 주세요.
  - 쓸 내용: 「A: … / B: … / C: … / D: … / E: … / F: …」 여섯 개와 「기대 결정과 같음 · 다름」
  - 답:
    A ('허용', [])
    B ('거부', ['관리자 역할이 아님'])
    C ('추가확인', ['MFA 안 함'])
    D ('추가확인', ['기기 보안 상태 이상'])
    E ('추가확인', ['해외에서 접속'])
    F ('거부', ['MFA 안 함', '해외에서 접속'])

    기대 결정과 다름
- (다) 🔍 점수 세 개를 정하면서 찾은 조건을 적어 주세요. 점수 하나가 가질 수 있는 범위와, 두 점수의 합이 만족해야 하는 조건이 있나요?
  - 쓸 내용: ① 기기 보안 상태 이상 점수의 범위 ② MFA 점수와 해외 점수의 범위 ③ 둘의 합이 만족해야 하는 조건과 그 이유(요청 몇 번 때문인지)
  - 답: 기기 보안 상태 이상 점수는 D 요청이 거부되어야 하므로 50점 이상이어야 한다.

  MFA 안 함 점수와 해외 접속 점수는 C와 E 요청이 각각 추가확인으로 판정되어야 하므로 각각 10점 이상 50점 미만이어야 한다.

  또한 F 요청은 MFA 안 함과 해외 접속이 동시에 발생하여 거부되어야 하므로 두 점수의 합이 50점 이상이어야 한다.

  따라서 HEALTH_POINTS = 50, MFA_POINTS = 20, COUNTRY_POINTS = 30으로 설정했다.
- (라) 🔍 기기 보안 상태 이상은 정산 조회에서는 추가확인인데 권한 변경에서는 거부입니다. 왜 기준이 다른가요?
  - 쓸 내용: ① 정산 조회에서 그 신호의 점수와 결정 ② 내가 정한 권한 변경 점수와 결정 ③ 기준이 다른 이유
  - 답: 정산 조회에서는 기기 보안 상태 이상에 10점 이상 50점 미만의 점수가 부여되어 추가확인으로 처리되지만, 권한 변경에서는 내가 정한 HEALTH_POINTS = 50으로 인해 바로 거부된다.

  권한 변경은 사용자 계정의 접근 권한을 바꿀 수 있어 일반적인 정산 조회보다 보안 위험이 크다. 따라서 같은 기기 보안 상태 이상이 발생하더라도 권한 변경에서는 더 엄격한 점수를 적용하여 접근을 차단해야 한다.

### 문제 3-2 · 요청 7건을 한꺼번에 판정해 건수 세기

- (가) 실행해서 나온 출력 전체를 붙여 넣어 주세요.
  - 쓸 내용: 거부 · 추가확인 줄, 건수 줄, 이유별 건수 줄 전체
  - 답:

```
[추가확인] 2 seoyeon ['대량 조회 (+30)']
[거부] 3 seoyeon ['이 계정에 등록된 기기가 아님']
[거부] 4 dami ['재직 중인 계정이 아님']
[추가확인] 5 junho ['기기 보안 상태 이상 (+40)']
[거부] 6 junho ['해외에서 접속 (+30)', '새벽 접속 (+20)']
[거부] 7 seoyeon ['이 계정에 등록된 기기가 아님']
허용 1 건 / 추가확인 2 건 / 거부 4 건
거부 이유별 건수 {'이 계정에 등록된 기기가 아님': 2, '재직 중인 계정이 아님': 1, '해외에서 접속 (+30)': 1, '새벽 접속 (+20)': 1}
```

- (나) 🔍 거부된 요청 중 필수 조건에서 바로 거부된 것과 점수가 쌓여서 거부된 것은 각각 몇 번 요청이고 이유가 무엇인가요?
  - 쓸 내용: ① 필수 조건으로 거부된 요청 번호와 이유 ② 점수로 거부된 요청 번호와 이유 목록
  - 답: 3 등록된 기기가 아님, 4 재직 중인 계정이 아님, 7 등록된 기기가 아님
        6 해외 접속으로 30점, 새벽 접속으로 20점이 더해져 총 50점이 되었으므로 거부되었다.
- (다) 🔍 거부 이유별 건수에서 가장 많은 이유는 무엇이고, 이 숫자는 보안 담당에게 무엇을 알려 주나요?
  - 쓸 내용: ① 가장 많은 이유와 건수 ② 기록으로 확인되는 것과 확인되지 않는 것 ③ 보안 담당이 할 일
  - 답: 가장 많은 거부 이유는 '이 계정에 등록된 기기가 아님'으로 총 2건이다.

  이를 통해 등록되지 않은 기기 NB-7741에서 seoyeon 계정으로 접속한 요청이 2건 거부되었다는 사실을 확인할 수 있다. 하지만 이 기록만으로 실제 접속자가 누구인지, 계정이 도용되었는지, 악의적인 접속인지까지는 알 수 없다.

  보안 담당자는 해당 기기의 등록 및 사용 승인 여부와 계정 로그인 기록을 확인하고, 실제 사용자에게 접속 사실을 확인해야 한다.
- (라) 🔍 등록 기기 · 국내 · 낮 시간에 MFA 까지 한 같은 계정이 20건 미만 조회를 100번 반복하면 이 코드는 어떻게 판정하나요? 왜 그런지, 이를 막으려면 무엇이 필요한지 적어 주세요.
  - 쓸 내용: ① 100번의 판정 결과 ② 그렇게 판정되는 이유 ③ 막으려면 필요한 것
